# 自部署实时语音 Agent 指南

> 基于**开源 Qwen3-Omni** + **project9 自建 WebSocket 层**,从零搭一个全双工实时语音 agent。
> 配套:`project9-2/项目结构说明文档.md` §7.3(选型)、§7.4(Qwen-Audio-3.0-Realtime 能力)。

## 1. 背景与定位

| 路线 | 谁搭 WebSocket 实时层 | 说明 |
|---|---|---|
| Qwen-Audio-3.0-Realtime API | 阿里搭好,你当客户端 | 商业 API,无权重 |
| **自部署开源 Qwen3-Omni** | **你自己搭(project9 模式)** | 本指南 |
| 用 Claude | 没原生 realtime,也得自己搭 | 见 9_2 §7.3 |

**核心思路**:模型用开源 Qwen3-Omni(vLLM 起流式服务),实时 WebSocket 层把 project9 的 `ConnectionManager` + 事件协议 + 后台流式推送搬过来,中间接音频流水线 + VAD + barge-in。

## 2. 整体架构

两条路线,WebSocket 层共有:

| 路线 | 模型组成 | 延迟 | 复杂度 | 适合 |
|---|---|---|---|---|
| **A 端到端** | Qwen3-Omni-30B-A3B(Thinker+Talker 一体) | 低 | 中 | 追求像 Realtime API 体验 |
| **B 级联** | Qwen3-ASR + LLM + Qwen3-TTS | 高 | 高(三段拼接) | 各组件可替换/调试 |

Qwen3-Omni 是 **Thinker-Talker 架构**(Thinker 推理、Talker 出声),原生吃音频流、流式吐文本+语音,**不用单独接 ASR/TTS**。推荐路线 A。

```
客户端 ──WS──▶ project9 WS 网关 ──HTTP/SSE──▶ vLLM(Qwen3-Omni)
           (ConnectionManager              (模型推理,流式输出)
            + 事件协议 + VAD
            + 音频流水线 + barge-in)
```

## 3. 自建 WebSocket 层:复用 project9 什么 + 新增什么

| project9 已有(直接复用) | 自部署要新增 |
|---|---|
| `ConnectionManager`(client_id->WS) | **VAD**(语音活动检测,触发 barge-in) |
| 后台任务 + 事件推送模式 | **音频流水线**(收 PCM -> 模型 -> 推 PCM) |
| 事件协议(`session.update`/`input_audio_buffer.append`/`response.audio.delta`) | **barge-in 处理**(检测用户开口 -> 中断生成 + 停 TTS) |
| `while True: receive_text()` 双向通道 | 模型流式调用桥接 |

事件协议直接抄 Qwen-Audio-3.0-Realtime 那套(你已是"服务端",自己定义也行,抄成熟的省事):[多模态交互协议](https://help.aliyun.com/zh/model-studio/multimodal-interaction-protocol/)。

### 代码骨架(FastAPI,基于 project9 扩展)

```python
# ws_server.py -- 在 project9 的 ConnectionManager 之上加音频流水线
import asyncio, json, base64
from fastapi import FastAPI, WebSocket
from app.connection_manager import manager   # 复用 project9
from vad import SileroVAD                     # 外挂 VAD(或用模型自带 semantic VAD)
from omni_client import qwen_omni_stream      # 调 vLLM/官方流式推理

app = FastAPI()

@app.websocket("/ws/{client_id}")
async def endpoint(ws: WebSocket, client_id: str):
    await manager.connect(client_id, ws)
    vad, audio_buf, gen_task = SileroVAD(), bytearray(), None

    async for raw in ws.iter_text():
        msg = json.loads(raw)
        t = msg["type"]

        if t == "session.update":
            session = msg["session"]               # 配置:音频格式、VAD、模态

        elif t == "input_audio_buffer.append":
            pcm = base64.b64decode(msg["audio"])
            audio_buf.extend(pcm)
            if vad.is_speech(pcm) and gen_task:     # barge-in!
                gen_task.cancel()
                await manager.send_message(client_id,
                    {"type": "input_audio_buffer.speech_started"})
            if vad.utterance_end(pcm):
                audio_to_send, audio_buf = audio_buf, bytearray()
                gen_task = asyncio.create_task(
                    generate_and_stream(client_id, audio_to_send))

async def generate_and_stream(client_id, audio_pcm):
    """后台流式生成 + 推事件 -- 就是 project9 的 run_agent_and_stream"""
    try:
        async for chunk in qwen_omni_stream(audio_pcm):
            if chunk.text:
                await manager.send_message(client_id, {
                    "type": "response.audio_transcript.delta", "delta": chunk.text})
            if chunk.audio:
                await manager.send_message(client_id, {
                    "type": "response.audio.delta",
                    "delta": base64.b64encode(chunk.audio).decode()})
        await manager.send_message(client_id, {"type": "response.done"})
    except asyncio.CancelledError:
        pass   # barge-in 正常中断
```

客户端和调 Qwen-Audio-3.0-Realtime 一模一样--连 WS、发 `input_audio_buffer.append`、收 `response.audio.delta` 播放。**区别只是服务端从"阿里的"变成"你的"**。

> 📦 **可运行骨架**(含 fake 后端,无需 GPU 即可跑通 WS 层 + 事件协议 + VAD + barge-in 完整链路)见 [`../project9-4/`](../project9-4/)(`app/main.py` + `test_client.py`)。

## 5. 硬件选型与并发估算

### 行业基准(实时语音,<500ms 延迟约束)
- [Cerebrium 实测](https://cerebrium.ai/blog/deploying-a-global-scale-ai-voice-agent-with-500ms-latency):自部署 LLM 在 **H100 约 10 路并发**;对比 Deepgram 托管 STT 在 A10 上 180 路。
- [Spheron](https://www.spheron.network/blog/voice-ai-gpu-infrastructure/):单卡语音 agent 生产级约 **8 路并发**。
- [arxiv 论文](https://arxiv.org/html/2603.05413v2):vLLM 在单卡 H200 自部署 Qwen3-Omni Thinker。

### 硬件对照表

| 硬件 | 模型 | 实时语音并发(估) | 定位 |
|---|---|---|---|
| 单卡 4090 24G | Qwen3-Omni-30B INT4 | ~1-2 | demo/验证 |
| 单卡 4090 24G | **Qwen2.5-Omni-7B** | ~2-4 | **4090 推荐** |
| 2×4090 数据并行 | Qwen2.5-Omni-7B | ~4-8 | 接近单卡 A100 |
| 2×4090 数据并行 | Qwen3-Omni-30B INT4 | ~2-4 | |
| 单卡 A100 40G | Qwen3-Omni | ~5-8 | 生产入门 |
| 单卡 H100/H200 | Qwen3-Omni | ~8-10 | 生产 |

### VRAM 估算法(自己算)

```
可用 KV 显存 = 总显存 − 权重(AWQ 4bit ~16-20G) − 激活/临时
单路 KV     ≈ 上下文 token 数 × ~150-400 KB/token   (KV cache per-token 约 144 KiB 量级)
VRAM 并发上限 ≈ 可用 KV 显存 ÷ 单路 KV
```
A100 40G:剩 ~20-24G,单路按 1G 算 -> VRAM 允许 ~20 路;但延迟把实际压到 ~8 路。**瓶颈是延迟/算力,不是显存。**

### 三个绑定因素(为什么并发这么少)
1. **延迟绑定,不是吞吐绑定**:实时语音 <500ms,不能像文本那样攒大批一起算。纯文本 benchmark 能到几百路([vLLM 测 369~407](https://github.com/vllm-project/vllm-ascend/issues/6071)),但那是吞吐上限,不是实时并发。
2. **音频 KV 占显存**:音频 token 密集,多轮上下文几千 token,每路 KV 几百 MB~1GB+。
3. **vLLM 跑 Qwen3-Omni GPU 利用率不高**(已知问题)。

### 4090 单卡要点
- [搜狐选型](https://www.sohu.com/a/1051043296_122943024):"1 张 RTX 4090 24GB 即可运行 INT4 量化版本";[GitHub 讨论](https://github.com/QwenLM/Qwen3-Omni/discussions/119)也有人 24G 卡试 30B INT4。
- [4090 跑 Qwen2.5-VL 实测](https://developer.volcengine.com/articles/7535837118279778342):权重约 15.6G,`max_model_len=32768` 直接 OOM,**必须把上下文限到 4~8K**。
- [CSDN](https://blog.csdn.net/AngelCryToo/article/details/147276420):4090 单卡部署 Qwen2.5-Omni-7B 可行,FP16 ~14G 余量大;[知乎](https://zhuanlan.zhihu.com/p/1889759620144267906)优化后能压到 8G。
- **4090 跑 7B 是甜点**,30B 只能 demo。
- [MoE 带宽注意](https://apxml.com/zh/posts/qwen-3-5-system-requirement-vram-guide):MoE 需要高带宽不断激活专家,4090 GDDR6X(1008 GB/s)够用但不如 A100 HBM(1555)、H100(3000+);30B-A3B 是 MoE,4090 上延迟比 A100 高;7B 是 dense,没这问题。

## 6. 多卡/多实例部署

### 关键前提:4090 无 NVLink
[NVIDIA 40 系移除了 NVLink](https://forums.developer.nvidia.com/t/dual-rtx-4090-with-distributed-training/289454),两卡只能走 PCIe(Gen4 ~32 GB/s 单向,vs NVLink 600 GB/s)。

### 三种用法对比

| 用法 | 怎么做 | 2×4090 适合? | 原因 |
|---|---|---|---|
| **数据并行 DP** | 每卡一个独立实例,前端 LB | ✅ **推荐** | 推理时无需跨卡通信,PCIe 够 |
| **张量并行 TP=2** | 一个模型拆两卡 | ❌ 别用 | 无 NVLink,每层 all-reduce 走 PCIe,延迟暴涨 |
| **流水线并行 PP=2** | 按层切(GPU1 跑 1-40 层,GPU2 跑 41-80 层) | ⚠️ 单卡放不下才用 | 30B INT4 单卡能放下,不需要拆 |

依据:
- [vLLM 文档](https://docs.vllm.ai/en/stable/serving/parallelism_scaling/):无 NVLink 改用 PP 而非 TP。
- [Spheron](https://www.spheron.network/blog/rtx-4090-for-ai-ml/):PCIe Gen4 对 DP 够用。
- [知乎 Qwen3 并行策略](https://zhuanlan.zhihu.com/p/1954352767616398785):模型能单卡放下就 DP 获最大吞吐。
- 实测铁证([GitHub vLLM #6292](https://github.com/vllm-project/vllm/issues/6292)):**4×4090 TP=4 跑 72B-int4"响应十几秒"**,单卡 A100 反而 OK。

### vLLM 两种 DP 做法

**方式 A:vLLM 原生数据并行(最省事)**
[vLLM 官方](https://docs.vllm.ai/en/latest/serving/data_parallel_deployment/):"暴露一个单一 API 端点",内置 Router。
```bash
vllm serve Qwen/Qwen3-Omni-30B-A3B-Instruct \
  --quantization awq \
  --data-parallel-size 2 \      # 2 副本,每卡一个,内置 Router 在 :8000 分发
  --port 8000
```

**方式 B:手动多实例 + 外部网关(最灵活)**
```bash
CUDA_VISIBLE_DEVICES=0 vllm serve <model> --quantization awq --port 8001
CUDA_VISIBLE_DEVICES=1 vllm serve <model> --quantization awq --port 8002
# 前端 nginx/HAProxy 轮询,或自己写(project9 ConnectionManager 多实例化)
```

| | 方式 A(原生 DP) | 方式 B(手动+网关) |
|---|---|---|
| 搭建成本 | 一条命令 | 多进程 + 配 LB |
| 灵活度 | vLLM 内置路由 | 完全自定义 |
| **session 亲和性** | 看 Router 策略 | **可自己控**(client_id 固定副本) |
| 跨机器 | 单节点为主 | 轻松跨机 |
| 适合 | 快速上、单机 | 生产、要控路由 |

**实时语音关键点:session 亲和性(KV cache 局部性)**。一路语音会话多轮累积上下文,若每次随机分到不同副本,每副本都重算前缀 KV,浪费且加延迟。方式 B 可把 `client_id` 粘到固定副本让 KV 持续命中;方式 A 取决于 vLLM Router 是否做亲和路由。

### 完整架构(别忘了 WS 网关始终在前面)

```
客户端 ──WS──▶ project9 WS 网关 ──HTTP/SSE──▶ vLLM 后端
              (ConnectionManager           ↑
               + 事件协议 + VAD)         方式A:单一端点(:8000)
                                       方式B:多实例(8001/8002),网关自己路由
```
- **WS 网关(project9)永远要自己搭**--vLLM 只给 HTTP(OpenAI 兼容,含 SSE 流式),不做 WebSocket 双向流。
- vLLM 是模型后端:方式 A 单一端点(网关调用简单),方式 B 网关自己路由多副本(能做 session 亲和)。

## 7. 难点与注意

1. **VAD + barge-in**:全双工关键。Qwen3-Omni 自带 **semantic VAD**(语义级,和声/噪音不误打断);自部署用模型自带最省事,否则外挂 silero-VAD。
2. **流式音频对齐**:模型吐音频分片,客户端按序播放;barge-in 时清空播放队列。
3. **延迟优化**:端到端 <500ms 才像真人。MoE 激活仅 3B 有利,但 vLLM GPU 利用率问题要压测。
4. **并发**:每路连接占一条流式生成;`ConnectionManager` 是进程内 dict,多实例要上 Redis pub/sub(见 9_2 §7.2)。
5. **音频格式**:统一 PCM16;采样率(输入 16k、输出 24k)在 `session.update` 声明并两端重采样对齐。
6. **消费卡生产注意**:4090 无 ECC、驱动长跑稳定性不如服务器卡;2×4090 功耗 900W+,需 1000W+ 电源和散热;7×24 生产谨慎,POC/中小并发没问题。
7. **更轻的开源替代**:[MiniCPM-o 4.5](https://hub.baai.ac.cn/view/54329) 是业界首个端到端全双工全模态,断网可用、显存友好,同样需自建 WS 层但模型更轻。

## 8. 落地路线图

1. **跑通模型**:本地 vLLM 起 Qwen3-Omni,命令行验证音频进、语音出。
2. **搭 WebSocket 层**:把 project9 的 `ConnectionManager` + 事件协议搬过来,接模型流式(单工:用户说一句、AI 答一句)。
3. **加 VAD + barge-in**:升级到全双工(用户能打断)。
4. **压测延迟 + 并发**:达标后上多实例 + DP/网关。

前两步就是 project9 的扩展(把 `FakeListChatModel` 换成 Qwen3-Omni 流式调用),第三步才是新增的硬骨头。
