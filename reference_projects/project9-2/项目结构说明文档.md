# 实践九（生产版）：高并发流式 Agent 服务 — 项目结构说明文档

## 1. 项目概述

### 1.1 项目简介
本项目是 `project9-1` 的**生产化重构**：保留「REST 触发 + 后台任务 + WebSocket 回传」的核心架构，在之上叠加限流、缓存、重试、结构化日志、链路追踪、全局异常等生产关注点，并把代码组织成分层架构（api / core / schemas / services）。

### 1.2 主要功能（相对 9_1 的增量）
- **Redis 缓存**：按消息内容 md5 生成 key，命中则跳过图执行直接回推
- **固定窗口限流**：Redis pipeline 原子 incr+expire，按 client_id 限流
- **指数退避重试**：tenacity，最多 3 次，退避 2~10s
- **structlog 结构化日志**：DEBUG 用 ConsoleRenderer，生产用 JSON
- **Request-ID 链路追踪**：中间件注入 `X-Request-ID`，绑定到 structlog 上下文
- **全局异常处理**：`ServiceError` 体系（RateLimitExceeded / CacheError / LLMError）
- **健康检查 / CORS / Lifespan**：`GET /health`、CORS、启动连 Redis / 关闭断开

### 1.3 技术栈（相对 9_1 新增）
- **structlog**：结构化日志
- **redis[asyncio]**：缓存 + 限流
- **tenacity**：重试
- **pydantic-settings**：配置管理（.env）

## 4. 生产化组件详解

### 4.1 限流 `rate_limiter.py`
- Redis pipeline 原子操作 `incr` + `expire`，固定窗口（默认 1s / 1000 次）
- key = `rate_limit:{client_id}`
- **降级策略**：Redis 未连接或限流出错时**放行并记日志**（不阻断主流程）
- 超限抛 `RateLimitExceeded`（继承 `ServiceError`）

### 4.2 缓存 `cache_service.py`
- `redis.asyncio`，`from_url(REDIS_URL)`
- key = `chat_cache:{md5(message)}`
- `set` 默认 TTL 3600s
- 命中时 `chat_service` 直接推送「从缓存加载」+ 缓存内容 +「已完成(Cached)」，**不跑图**

### 4.3 重试 `chat_service.py`
```python
@retry(stop=stop_after_attempt(3),
       wait=wait_exponential(multiplier=1, min=2, max=10),
       retry=retry_if_exception_type(Exception), reraise=True)
async def _execute_graph_with_retry(self, message, client_id): ...
```
- 最多 3 次，退避 2~10s 指数增长
- 失败抛 `LLMError`，被 `process_chat_request` 捕获后通过 `error` 事件回推客户端
- **重试期间 HTTP 早已返回**，客户端只看到事件流——这正是触发/回传解耦的价值

### 4.4 结构化日志 + Request-ID
- `RequestIDMiddleware`：从 `X-Request-ID` header 取或生成 uuid，绑定到 `structlog.contextvars`
- 响应也回写 `X-Request-ID`，便于全链路追踪
- `logger.py`：DEBUG→ConsoleRenderer（彩色易读），非 DEBUG→JSONRenderer（便于采集）

### 4.5 全局异常 / Lifespan / 健康检查
- `@app.exception_handler(ServiceError)`：统一捕获服务异常返回 500
- `lifespan`：启动 `cache_service.connect()`（ping Redis），关闭 `close()`
- `GET /health`：返回 `{status, version}`

### 4.6 业务主流程 `chat_service.process_chat_request`
```
1. 生成 cache_key = md5(message)
2. cache_service.get(key)
   ├─ 命中 → 推 status(从缓存加载) + message(缓存内容) + status(已完成 Cached) → return
   └─ 未命中 → 推 status(工作流已启动)
3. _execute_graph_with_retry(message, client_id)
   └─ 遍历 astream_events：on_chain_start/on_chain_end/on_chat_model_stream → 推 status/message/token
4. cache_service.set(key, final_result)
5. 推 status(工作流已完成)
6. 异常 → 推 error
```

## 5. 运行说明（需 Redis）

### 5.1 安装依赖（无 requirements.txt，手动安装）
```bash
cd project9-2
python -m venv venv && source venv/bin/activate
pip install fastapi uvicorn langgraph langchain-core langchain-community \
            structlog redis pydantic pydantic-settings tenacity websockets
```

### 5.2 启动 Redis
```bash
redis-server                 # 或 docker run -d -p 6379:6379 redis
redis-cli ping               # 期望返回 PONG
```

### 5.3 启动服务
```bash
# 在 project9-2/ 目录下
python -m app.main            # main.py 内置 uvicorn.run(..., port=8000, reload=True)
# 或
uvicorn app.main:app --reload --port 8000
```
启动成功日志应包含 `Connected to Redis`。

### 5.4 配置（可选 .env）
默认值见 `core/config.py`，可通过 `.env` 覆盖：
```bash
REDIS_URL=redis://localhost:6379/0
RATE_LIMIT_PER_SECOND=1000
LOG_LEVEL=INFO
DEBUG=True
```

### 5.5 测试
本项目无 `test_client.py`，可手写脚本（参考 9_1 的 `test_client.py`，将 `app` 改为对应路径即可），或用 `websocat`：
```bash
# 终端1：连 WS
websocat ws://localhost:8000/ws/user_001
# 终端2：触发
curl -X POST http://localhost:8000/chat \
  -H "Content-Type: application/json" \
  -d '{"message":"分析一下","client_id":"user_001"}'
# 终端1 会收到 status/message 事件流
# 健康检查
curl http://localhost:8000/health
```

## 6. 数据流
```
客户端 ──WS /ws/{client_id}──▶ ConnectionManager 注册
客户端 ──POST /chat──▶ endpoints.chat_endpoint
                        ├─ 校验 WS 已连
                        ├─ rate_limiter.check_rate_limit(client_id)  ──▶ Redis incr
                        ├─ BackgroundTasks.add_task(chat_service.process_chat_request)
                        └─ 返回 ChatResponse{status:accepted}
                          （后台）process_chat_request
                            ├─ cache_service.get(md5(msg))  ──▶ Redis
                            │    命中 → 推缓存结果 → return
                            │    未命中 ↓
                            ├─ _execute_graph_with_retry → graph.astream_events
                            │    每个事件 → connection_manager.send_message(client_id, {type,content})
                            └─ cache_service.set(...) → 推"已完成"
```

### 7.3 选型回顾与行业现状（2026.07）

**本项目选型**：WebSocket 而非 SSE，与业内共识一致——长任务 / 可中断 / 双向 / 触发与回传解耦选 WebSocket；纯单轮流式选 SSE。两者在 LLM 消息速率下延迟几乎相同，选 WS 不是为了速度（[tianpan.co](https://tianpan.co/blog/2026-04-19-sse-websockets-grpc-streaming-llm-applications)、[Ably 2026](https://ably.com/blog/websockets-vs-http-for-ai-streaming-and-agents)）。

**各厂商实时 WebSocket 支持对照**：

| 厂商 | 原生实时 WebSocket | 接入方式 |
|---|---|---|
| OpenAI | ✅ Realtime API | 直接连 WebSocket |
| 阿里 通义千问 | ✅ [Qwen-Omni / Audio-3.0-Realtime](https://help.aliyun.com/zh/model-studio/realtime)（WebSocket+WebRTC+AOQ） | 直接连（百炼/DashScope） |
| 字节 豆包 | ✅ [端到端实时语音 API](https://www.volcengine.com/docs/6561/1594356)（火山引擎，WebSocket S2S） | 直接连 |
| Anthropic/Claude | ❌ 没有 | **自建（本项目）或用框架** |
- **OpenAI**：文本流式仍用 SSE；**额外**有 [Realtime API](https://developers.openai.com/api/docs/guides/realtime)（WebSocket，双向语音），2026 又出 GPT-Realtime-2 / Translate / Whisper、GPT-Live 全双工。
- **阿里 Qwen-Omni / Qwen-Audio-3.0-Realtime**：国内版 “OpenAI Realtime”，Realtime API 支持 **WebSocket + WebRTC + AOQ（QUIC）** 三种传输（[简介](https://platform.qianwenai.com/docs/developer-guides/realtime-api/overview)），[多模态交互协议](https://help.aliyun.com/zh/model-studio/multimodal-interaction-protocol/) 是全双工 JSON 事件流。**Omni** = 全模态（音视频+图文）；**Audio-3.0-Realtime**（2026.7 发布，纯语音，能力见 §7.4）是同套 API 的语音专版。百炼 API Key 即可接入。
- **字节豆包 Seeduplex**：原生全双工语音大模型，[火山引擎提供 WebSocket S2S API](https://www.volcengine.com/docs/6561/1594356)。
- **Anthropic/Claude**：[流式全线 SSE](https://platform.claude.com/docs/en/build-with-claude/streaming)，**没有原生实时 WebSocket API**。2026.05 的 Code with Claude 大会“一个语音产品都没发布”（[findskill.ai](https://findskill.ai/blog/gpt-realtime-2-vs-claude-voice-routing/)）。2026.01 给 Claude 加了音频输入(听写)+TTS 输出，但仍在标准 Messages API 上、走 SSE，不是双向实时 WebSocket（[Anthropic Transparency Hub](https://www.anthropic.com/transparency)）。

**对本项目的现实意义**：正因为 Anthropic 不提供实时 WebSocket，用 Claude 做实时/流式 agent 时**必须自建 WebSocket 层**（连接管理 + 事件推送），把 Claude 的 SSE 流包起来——本项目教的就是这一层。用 OpenAI 则可直接用官方 Realtime API 的 WebSocket，省掉这部分自建。第三方实时层（[AssemblyAI Voice Agent API](https://www.assemblyai.com/blog/assemblyai-april-2026-recap)、LiveKit、Inworld）走同一思路：WS 层做 STT+TTS+传输，中间挂 Claude 文本模型。

**选型建议**：若目标是 “做一个能用的全双工语音 agent”，选 Qwen-Omni-Realtime / 豆包 / OpenAI 接入成本最低--原生 WebSocket，作为客户端连上即可，**不用自建 project9 这套**。只有非要用 Claude 当大脑时，才需要 project9 + LiveKit/Pipecat/[AssemblyAI](https://www.assemblyai.com/blog/assemblyai-april-2026-recap) 等框架那一层自建 WebSocket。**本项目教的是后者：“模型不提供 realtime 层时如何自己搭”。**

### 7.4 替代方案速览：Qwen-Audio-3.0-Realtime 能力

若按 §7.3 选型建议改走 “直接接 Qwen” 路线，以下为 **Qwen-Audio-3.0-Realtime**（2026.7 发布，纯语音专版，与 Qwen-Omni-Realtime 同套 WebSocket API）的能力速览。

**四条主线**：推理智商（毫秒级响应不降智）/ Agent 工具调用（无指令自调用，结果入记忆）/ 共情情感（动态语气节奏音调）/ 双工流畅度（边听边打断）。

| 功能 | 说明 |
|---|---|
| 实时语音识别 ASR | 语音流转文字，输入 16kHz PCM |
| 实时语音生成 TTS | 回复转语音流，输出 24kHz PCM |
| 多轮对话 + 上下文管理 | 跨轮记忆，追问接着说 |
| 函数调用 Function Call | 标准协议，模型自决何时调外部工具 |
| 无指令 Agent 工具自调用 | 不需明确指令，结果自动入记忆，后续追问可用 |
| 动态情感语气 | 按语境调语气/节奏/音调/情感，拟人化 |
| 全双工打断 barge-in | 边听边说，用户随时插话打断 |
| 毫秒级响应 | 时延敏感场景直接生成 |

**能干什么**：聊天类（智能客服 / AI 伴侣 / 娱乐互动 / 教育培训）+ 办事类（路线规划、信息查询等，靠工具调用完成实际任务，非仅闲聊）。

**双版本**：Plus（推理强，复杂任务）/ Flash（速度快，时延敏感）。

**接入**：同 §7.3 阿里行 -- `wss://dashscope.aliyuncs.com/api-ws/v1/realtime`，API Key 鉴权，事件协议见 [多模态交互协议](https://help.aliyun.com/zh/model-studio/multimodal-interaction-protocol/)、[Qwen-Audio Realtime WebSocket API](https://help.aliyun.com/zh/model-studio/fun-audiochat-realtime-websocket-api)。
