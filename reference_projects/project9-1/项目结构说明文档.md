# 实践九（基础版）：WebSocket + LangGraph 流式 Agent 服务 — 项目结构说明文档

## 1. 项目概述

### 1.1 项目简介
本项目演示如何用 **FastAPI + LangGraph + WebSocket** 构建一个流式 Agent 服务。核心设计是**「双端点 + 后台任务」**：用户通过 `POST /chat` 提交消息，服务端立即返回 `accepted`，真正的 LangGraph 工作流在后台任务中执行，并通过一条按 `client_id` 寻址的 WebSocket 长连接把 `status / token / message / error` 事件实时推回客户端。

### 1.2 主要功能
- **REST 触发 + WebSocket 回传**：触发与流式回传解耦，HTTP 请求毫秒级返回
- **后台任务执行**：Agent 在 `BackgroundTasks` 中运行，不阻塞 HTTP worker
- **细粒度事件流**：基于 `graph.astream_events(version="v2")` 推送节点启动/完成、token 流、状态变更
- **多客户端连接管理**：`ConnectionManager` 维护 `client_id -> WebSocket` 映射，支持并发客户端

### 1.3 技术栈
- **FastAPI**：Web 框架（REST 端点 + WebSocket 端点 + BackgroundTasks）
- **LangGraph**：Agent 工作流编排（StateGraph，`astream_events` 事件流）
- **langchain-core**：消息类型（HumanMessage/AIMessage）、FakeListChatModel（模拟 LLM）
- **websockets / httpx**：测试客户端所用
- **pydantic**：请求模型校验

> 本项目用 `FakeListChatModel` 模拟 LLM，**无需任何 API Key**，开箱即跑。

## 2. 文件结构

```
project9-1/
├── requirements.txt          # 依赖清单
├── test_client.py            # 测试客户端（连 WS + POST /chat + 监听事件）⭐
└── app/
    ├── __init__.py
    ├── main.py               # FastAPI 入口：/chat 与 /ws/{client_id} 端点 + 后台任务 ⭐
    ├── connection_manager.py # WebSocket 连接管理器（client_id -> WS）⭐
    ├── graph.py              # LangGraph 工作流定义（agent -> processor）⭐
    └── models.py             # Pydantic 请求模型 ChatRequest
```

### 关键文件说明
- **`app/main.py`**：定义两个端点和后台任务
  - `POST /chat`：校验 client_id 已连 WS → `background_tasks.add_task(run_agent_and_stream, ...)` → 立即返回 `{"status":"accepted"}`
  - `WS /ws/{client_id}`：接受连接并注册到 `ConnectionManager`，循环 `receive_text()` 保持活跃（预留接收客户端取消指令）
  - `run_agent_and_stream()`：后台任务，遍历 `graph.astream_events(..., version="v2")`，把事件翻译成 `{type, content}` 推给对应 client_id
- **`app/connection_manager.py`**：`ConnectionManager` 单例，`active_connections: Dict[str, WebSocket]`，提供 `connect / disconnect / send_message`
- **`app/graph.py`**：`AgentState`（messages 用 `operator.add` 累积）+ 两个节点 `agent`(call_model) → `processor`(process_data)，各 `sleep(1)` 模拟耗时，`FakeListChatModel` 模拟 LLM 响应
- **`app/models.py`**：`ChatRequest{message: str, client_id: str}`
- **`test_client.py`**：连接 `ws://localhost:8000/ws/user_test_001` → POST `/chat` → 循环 `recv()` 打印事件

## 3. 核心架构：为什么是「双端点 + 后台任务 + WebSocket」

### 3.1 两个端点各司其职
| 端点 | 方法 | 职责 |
|---|---|---|
| `/chat` | POST | 接收用户消息，触发后台任务，**立即返回** accepted |
| `/ws/{client_id}` | WebSocket | 长连接，后台任务通过它把事件推回客户端 |

### 3.2 触发与回传解耦
Agent 是长任务（图中两节点各 sleep 1s，真实场景可能几十秒）。如果把流式响应绑在 `POST /chat` 的 HTTP 连接上，该连接会被全程占用。本项目把 Agent 丢进 `BackgroundTasks`，HTTP 请求毫秒级返回，结果通过 `ConnectionManager` 按 `client_id` 寻址推送——**触发源与回传通道彻底分离**。

### 3.3 为什么用 WebSocket 而不是 SSE
1. **后台任务脱离请求 scope**：SSE 的流绑定在打开它的那次 HTTP 请求上，请求结束流就关。但这里 `/chat` 已 return，Agent 跑在后台，只能靠独立持有的长连接回推。
2. **按 client_id 寻址**：`ConnectionManager` 让"谁触发"与"结果送给谁"解耦，触发源可以不是流式客户端本身。
3. **预留双向控制面**：`while True: receive_text()` 为客户端发送 cancel/interrupt 等控制指令留通道（SSE 是单向 server→client）。
4. **连接复用**：同一 client_id 多轮 `/chat` 复用一条 socket。

> 注意：若只是「单次请求 → 单向流式吐 token」，SSE 更简单（OpenAI/Anthropic 官方 API 均用 SSE）。本项目用 WebSocket 是为演示上述解耦架构，**不是为了流式速度**——两者在 LLM 消息速率下延迟几乎相同。

### 3.4 业内实践与参考资料

本项目选型与业内主流共识一致。以下为关键事实与出处：

**文本流式：SSE 是绝对主流**
- OpenAI / Anthropic / Google 的文本流式 API 均用 SSE。[Claude 官方文档](https://platform.claude.com/docs/en/build-with-claude/streaming)明确 `stream: true` 走 SSE；[buildmvpfast](https://www.buildmvpfast.com/blog/streaming-llm-responses-sse-vs-websockets-2026) 总结 “Every major LLM provider picked SSE over WebSockets for streaming”。
- 原因：SSE 浏览器原生、走普通 HTTP、无需握手、好扩缩（[Ably 2026](https://ably.com/blog/websockets-vs-http-for-ai-streaming-and-agents)）。

**延迟几乎相同**
- 在 LLM 的消息速率下，SSE / WebSocket / gRPC 流式延迟基本一致——选 WebSocket 不是为了速度（[tianpan.co 基准](https://tianpan.co/blog/2026-04-19-sse-websockets-grpc-streaming-llm-applications)）。

**WebSocket 的用武之地：实时 / 双向 / agent**
- [OpenAI Realtime API](https://developers.openai.com/api/docs/guides/realtime) 用持久 WebSocket 做双向语音流（client 连 `/v1/realtime`，收发音频/文本/tool calls/session 事件）——“WebSocket for AI agent” 最权威的生产案例。
- 国内厂商也提供同类原生 WebSocket 实时 API：阿里 [Qwen-Omni-Realtime](https://help.aliyun.com/zh/model-studio/realtime)（WebSocket + WebRTC）、字节豆包 Seeduplex（[火山引擎 WebSocket S2S API](https://www.volcengine.com/docs/6561/1594356)）--厂商对照见 9_2 §7.3。
- 业内论调：WebSocket 正从 SSE 手里抢 agent 场景，关键词 “durable sessions”（[websocket.org: Why LLMs Are Moving Beyond SSE](https://websocket.org/guides/websockets-and-ai/)、[AI Token Streaming: From SSE to Durable Sessions](https://websocket.org/guides/use-cases/ai-streaming/)）。
- LangGraph 的 [interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)（pause graph、wait for external input）正是本项目 `while True: receive_text()` 预留的双向控制面的正式形态——HITL agent 确实需要反向通道。

**结论**：纯「单次请求 -> 单向流式」选 SSE；一旦长任务 / 可中断 / 双向 / 触发与回传解耦，选 WebSocket——本项目属于后者。

## 4. 运行说明

### 4.1 安装依赖
```bash
cd project9-1
python -m venv venv && source venv/bin/activate   # Windows: venv\Scripts\activate
pip install -r requirements.txt
```

### 4.2 启动服务
```bash
# 在 project9-1/ 目录下执行（保证 app 包可被导入）
uvicorn app.main:app --reload --host 0.0.0.0 --port 8000
```

### 4.3 运行测试客户端
另开一个终端：
```bash
cd project9-1
python test_client.py
```
`test_client.py` 流程：连 WS(`user_test_001`) → POST `/chat` → 循环打印收到的事件。

### 4.4 预期输出（服务端控制台 + 客户端）
客户端应依次收到：
```
[WS 接收] 类型: status     | 内容: 工作流已启动。
[WS 接收] 类型: status     | 内容: 节点 'agent' 已启动。
[WS 接收] 类型: message    | 内容: 我已收到您的请求。
[WS 接收] 类型: status     | 内容: 节点 'processor' 已启动。
[WS 接收] 类型: message    | 内容: 数据处理完成。
[WS 接收] 类型: status     | 内容: 工作流已完成。
```

### 4.5 客户端退出条件
`test_client.py` 收到 `content == "工作流已完成。"`（即服务端 `main.py:66` 推送的完成 status 事件）后打印"工作流完成"并 `break` 退出。该字符串须与服务端保持一致——服务端事件协议全程使用中文（`工作流已启动。` / `节点 'agent' 已启动。` / `工作流已完成。`），9_2 亦沿用此协议。

## 5. 数据流与时序

```
客户端                         FastAPI 服务端                     LangGraph
  │                                │                                │
  │── WS 连接 /ws/{client_id} ────▶│ accept + 注册到 ConnectionManager
  │                                │                                │
  │── POST /chat ─────────────────▶│ 校验 client_id 已连 WS          │
  │                                │ BackgroundTasks.add_task(...)  │
  │◀── 200 {status:accepted} ──────│ (立即返回，不等待 Agent)        │
  │                                │                                │
  │                                │  后台任务: astream_events(v2) ─▶│ on_chain_start(agent)
  │◀── WS {type:status, 工作流已启动}│◀─────────────────────────────│
  │◀── WS {type:status, agent 已启动}│◀─────────────────────────────│
  │◀── WS {type:message, ...}     │  on_chain_end(agent)           │
  │                                │  on_chain_start(processor)     │
  │◀── WS {type:message, 数据处理完成}│◀─────────────────────────────│
  │◀── WS {type:status, 工作流已完成}│  END                          │
```

## 6. 事件协议
所有事件均为 JSON，统一格式 `{"type": <类型>, "content": <内容>}`：

| type | 触发时机 | content 示例 |
|---|---|---|
| `status` | 工作流启动 / 节点启动 / 工作流完成 | `"工作流已启动。"` / `"节点 'agent' 已启动。"` |
| `message` | 节点完成（`on_chain_end`），取输出最后一条消息 | `"我已收到您的请求。"` |
| `token` | LLM 流式输出（`on_chat_model_stream`） | 单个 token 字符串（本 demo 用 FakeListChatModel，通常不触发） |
| `error` | 后台任务异常 | 异常字符串 |

## 7. 生产化缺口（指向 9_2）
本项目是单进程教学骨架，离生产还差：
- **无横切关注点**：无限流、无缓存、无重试、无结构化日志
- **`ConnectionManager` 是进程内 dict**：无法水平扩展到多实例
- **`BackgroundTasks` 进程内调度**：进程崩溃则任务丢失
- **无断线重连 / 消息缓冲**

以上缺口在 `project9-2` 中部分补齐（限流/缓存/重试/日志/分层架构），分布式与持久化缺口需结合 `project5_2`（Redis+gRPC）与 `project10`（docker-compose）进一步补齐。
