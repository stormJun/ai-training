# LoRA 微调后基于 vLLM 的生产部署降本方案

## 面试回答版本

如果让我用一句话概括这套方案，我会这样回答：

**LoRA 解决的是训练成本，不直接解决线上推理成本。**

**对于千问 7B 这类模型，真正的生产降本通常是 `单业务先 merge LoRA`，再做 `INT8/INT4 量化`，用 `vLLM` 承接高吞吐推理，同时通过 `prefix cache`、短输出约束、流量分层和实时干预来降低单位请求成本。**

如果面试官继续追问，我会补三点：

1. 对意图识别场景，不应默认让 7B 扛全量主链路。更常见的是 `规则/轻量模型主判定 + 7B fallback + 实时干预兜底`。
2. 如果业务已经确定在线跑 `Qwen 7B + LoRA`，生产上优先考虑 `merge -> quantize -> vLLM -> horizontal scale`，而不是直接把训练态模型上线。
3. 量化评估重点不是长文本生成质量，而是 `意图分类稳定性、错误路由率、高价值 query 误判率`。

---

## 1. 文档定位

本文不是泛泛介绍 LoRA 或 vLLM，而是面向下面这个具体问题：

- 基座模型是千问 7B
- 已经通过 LoRA 完成领域微调
- 业务是意图识别、活动意图识别、搜索前置路由或搜索纠偏触发
- 需要设计一套真正可上线、可扩容、可灰度、可回滚的生产方案

这里的“降本”不是单一指标，而是综合考虑：

- 单位请求的 GPU 成本
- 同等流量下所需机器数
- P95 / P99 延迟
- 高峰期扩容成本
- 错误路由带来的业务损失

---

## 2. 先给结论

### 2.1 LoRA 不等于线上便宜

LoRA 主要降低的是训练成本：

- 降低训练显存
- 减少训练参数量
- 提高实验迭代效率

到了线上，成本主要由下面几件事决定：

- 模型是不是在线主链路
- LoRA 是否 merge
- 是否做量化
- 推理框架是否支持高吞吐
- 请求输入输出 token 是否被严格控制
- 是否做流量分层和实时干预

### 2.2 意图识别场景的生产建议

如果业务本质是意图识别，不应该默认采用“7B 全量在线判定”的架构。

更稳妥的生产设计通常是：

```text
规则 / 词典 / 实时干预
        ↓
轻量意图模型主链路
        ↓
7B LoRA 模型作为 fallback 或复杂样本判定
        ↓
搜索/活动路由
```

原因很简单：

- 意图识别通常是短输入、短输出
- 大量请求并不需要 7B 的表达能力
- 错误路由的成本往往高于单次推理成本
- 让 7B 扛全量流量通常不是最优 TCO

### 2.3 什么时候才推荐 7B 直接在线

下面这些情况，才更适合把 `Qwen 7B + LoRA` 直接作为在线模型服务：

- 你们已经确定当前阶段不会蒸馏到小模型
- 意图定义复杂，轻量模型效果明显不够
- query 需要结合较长上下文或复杂业务规则
- 更看重上线速度，暂时接受较高单位推理成本

如果满足这些前提，才进入本文后续的 `vLLM` 部署设计。

## 3. 生产级推荐架构

### 3.1 推荐架构总览

对于你们这种“意图识别 + 新词实时纠偏”的业务，推荐架构如下：

```text
客户端
  ↓
API 网关
  ↓
实时干预层
  ├─ 热点词 / 新词映射
  ├─ 活动词白名单
  ├─ 规则直返
  └─ 查询改写 / 意图覆盖
  ↓
主判定层
  ├─ 轻量意图模型
  └─ Qwen-7B-LoRA(vLLM) fallback
  ↓
搜索 / 活动 / 内容路由
  ↓
日志、监控、样本回流
```

### 3.2 各层职责

- `API 网关`：鉴权、限流、灰度发布、超时控制。
- `实时干预层`：根据分钟级行为统计，快速发现新词、热点词和强意图映射。
- `轻量意图模型`：承担绝大多数稳定 query 的主链路判定。
- `Qwen 7B LoRA`：处理边界样本、复杂 query、低置信度 query 或新策略实验。
- `路由层`：根据意图结果决定走活动页、普通搜索、品牌聚合页或内容页。
- `样本回流`：把实时干预发现的新词、误判样本沉淀到词表、规则和下轮训练集中。

### 3.3 为什么这是生产上更稳的设计

因为它同时解决了三个问题：

- `成本`：7B 不需要吃掉全量流量。
- `稳定性`：高频稳定 query 可以由轻量模型或规则快速处理。
- `时效性`：新词和新活动不用等模型重训，实时干预先兜底。

## 4. 如果确定要让 Qwen 7B LoRA 在线服务，推荐怎么部署

### 4.1 单业务优先 merge

如果一个 LoRA adapter 对应一个固定业务，优先选择：

```text
merge(base model, adapter) -> 单一模型权重
```

原因：

- 部署链路更短
- 更适合量化
- 行为更稳定
- 监控和回滚更简单

如果是多 adapter 场景，不建议把所有 adapter 都长期 merge 成大量完整模型。更常见的生产做法是：

- 高频 adapter：预先 merge，独立部署
- 长尾 adapter：保留 `base + adapter` 动态加载
- 配套 `adapter registry + adapter cache + 路由层`

### 4.2 量化策略

对于 7B 模型，不做量化，线上显存成本通常偏高。

常见选择有：

- `BF16 / FP16`
- `INT8`
- `INT4 / AWQ / GPTQ`

对于意图识别、活动识别、搜索前置路由这类短输出任务，量化重点不是生成质量，而是分类和路由是否稳定。

经验上：

- `INT8`：更稳，适合作为第一版生产方案
- `INT4`：更省，但要重点验证边界 query 和高价值 query

重点指标不要只看整体 accuracy，而要看：

- 意图分类准确率和 F1
- 活动意图召回率
- 新词命中率
- 高价值 query 误判率
- 错误路由率

建议验证顺序：

1. 用 `BF16` 跑基线
2. 测 `INT8`
3. 再测 `INT4`

如果 `INT4` 在高价值 query 上误判明显上升，生产上通常优先选 `INT8`。

### 4.2.1 量化知识点补充

这里需要把几个容易混淆的概念分开：

- `LoRA`：微调方法，解决的是训练阶段如何低成本适配业务
- `merge`：把 LoRA adapter 合并回 base model，得到完整模型
- `量化`：把完整模型压缩成更适合上线的版本，解决的是部署成本问题

也就是说，对你们这类业务，常见流程不是“LoRA 和量化二选一”，而是：

```text
base model
-> LoRA 微调
-> 得到 adapter
-> merge 回 base model
-> 对 merged model 做量化
-> 再部署
```

训练阶段和部署前阶段使用的量化也不是一回事：

- `训练阶段量化`：常见是 `QLoRA / bitsandbytes 4bit or 8bit`，目的是让 7B 模型训得动
- `部署前量化`：常见是 `INT8 / GPTQ / AWQ`，目的是降低线上显存和机器成本

还需要区分“量化精度”和“量化方法”：

- `INT8`：量化结果或精度等级
- `GPTQ / AWQ`：量化方法

因此下面这些说法并不等价：

- `先上 INT8`
- `先上 GPTQ`
- `先上 AWQ`

更准确的理解是：

- `W8A8`：权重 8bit、激活 8bit，常作为 `INT8` 路线
- `W4A16`：权重 4bit、激活 16bit，常作为 `INT4 weight-only` 路线
- `GPTQ` 和 `AWQ`：都常用于生成 `W4A16` 这类 4bit 量化模型

在 `llm-compressor` 里，常见写法通常是：

- `scheme="W8A8"`：对应 `INT8`
- `scheme="W4A16"`：对应 `INT4`

对你们的意图识别场景，建议的理解顺序是：

1. 如果说训练阶段，优先考虑 `QLoRA`
2. 如果说部署阶段，先做 `merge`
3. 第一版生产优先尝试 `INT8`
4. 成本压力更大时，再压测 `GPTQ/AWQ 4bit`

原因是：

- 你们更关心分类稳定性和错误路由率
- 第一版生产通常更需要稳，而不是极限压缩
- `INT4` 更省，但对边界 query 和高价值 query 的误判风险更高

### 4.3 为什么用 vLLM

如果已经确定在线跑 7B，那么 `vLLM` 是更适合生产服务化的推理层，主要原因有：

- 支持 continuous batching，提高 GPU 利用率
- 更高效地管理 `KV Cache`
- 适合多请求并发的在线服务
- 具备较成熟的 API 服务形态，便于接入网关

但要注意，`vLLM` 的价值是提高吞吐和资源利用率，不代表它会自动让所有业务都更便宜。真正的成本收益，仍然取决于：

- 模型是否量化
- 流量是否分层
- prompt 是否足够短
- 输出是否被限制

### 4.4 prefix cache 在你们场景中的意义

`prefix cache` 的意思是：如果很多请求的 prompt 前半段完全相同，就把这一段前缀的计算结果缓存起来，后续请求直接复用，不再从头重复计算。

在意图识别场景里，如果你们的 prompt 比较固定，例如：

- 固定 system prompt
- 固定意图标签集合
- 固定输出格式
- 只有用户 query 在变化

那么 `prefix cache` 通常能带来明显收益：

- 降低首 token 延迟
- 减少重复计算
- 提高吞吐

如果每个请求的 prompt 差异都很大，命中率低，收益就有限。

### 4.5 输出限制必须收紧

对意图识别任务，不需要让模型输出解释性长文本。

生产上应尽量约束为：

- 固定标签
- 短 JSON
- 枚举值
- 最多几个 token

例如只允许输出：

```json
{"intent":"activity"}
```

而不是让模型自由发挥。这既降低成本，也降低解析失败率和路由不稳定性。

## 5. vLLM 的生产部署建议

### 5.1 推荐部署模式

对于 7B 模型，生产上更推荐：

- `单实例绑定单 GPU`
- `多实例横向扩容`

而不是一上来就做复杂的多卡并行。原因是：

- 运维复杂度更低
- 故障域更小
- 更适合灰度和回滚
- 容量规划更直观

### 5.2 启动参数思路

一个偏生产的启动思路如下：

```bash
python -m vllm.entrypoints.openai.api_server \
  --model /models/qwen7b-lora-merged-int8 \
  --served-model-name qwen7b-intent \
  --host 0.0.0.0 \
  --port 8000 \
  --dtype auto \
  --gpu-memory-utilization 0.90 \
  --max-model-len 2048 \
  --max-num-seqs 32 \
  --trust-remote-code \
  --enable-prefix-caching
```

参数设计原则：

- `--max-model-len`：按真实 query 长度设置，不要盲目放大。
- `--max-num-seqs`：通过压测确定，不是越大越好。
- `--gpu-memory-utilization`：留出安全余量，避免高峰期显存打满。
- `--enable-prefix-caching`：只在公共前缀稳定时启用收益最大。

### 5.3 不要把训练态参数直接搬到线上

线上参数要围绕三个目标调：

- 稳定的 P95 / P99 延迟
- 可接受的 GPU 利用率
- 高峰期不爆显存

因此，生产压测中要重点调的不是训练超参，而是：

- `max_model_len`
- `max_num_seqs`
- 请求超时时间
- 网关并发限制
- fallback 触发阈值

## 6. 成本优化的优先级

如果当前已经确定在线跑 `Qwen 7B + LoRA`，降本优先级建议如下：

### 6.1 先做流量分层

这是影响最大的动作。

不要让所有请求都直接进入 7B。优先顺序应该是：

1. 规则直返
2. 实时干预命中直接修正
3. 轻量模型主判定
4. 低置信度或复杂 query 才进入 7B

### 6.2 再做 merge 和量化

对固定业务场景，`merge + INT8/INT4` 往往是降低显存成本最直接的动作。

### 6.3 再做 prompt 和输出压缩

对意图识别场景，这一步经常被低估。

应尽量做到：

- system prompt 固定且短
- 标签定义短而清晰
- 不上不必要 few-shot
- 输出为固定枚举值
- `max_new_tokens` 严格受限

### 6.4 最后再榨 vLLM 参数

`vLLM` 的参数调优能带来收益，但通常不如前面三步大。不要把架构问题寄希望于单纯调大 batch。

## 7. 实时干预怎么和 7B 服务协同

这部分对你们场景很关键。

### 7.1 实时干预的职责

实时干预不是替代模型，而是在线补偿模型的知识滞后。

它主要处理：

- 新活动词
- 新简称
- 突发热点词
- 活动上线初期模型未覆盖的表达

### 7.2 推荐协同方式

推荐按优先级使用三种协同方式：

1. `前置改写`
   把新词映射成模型更熟悉的表达，再交给轻量模型或 7B。

2. `后置覆盖`
   模型先输出意图结果，实时干预在行为信号足够强时覆盖结果。

3. `强导流`
   对极高确定性的活动词，直接进入指定路由，不再让模型重复判断。

### 7.3 为什么这一步能明显降本

因为它能减少两类浪费：

- 新词误判导致的错误流量
- 本来可以直接命中的请求却还要打到 7B

所以实时干预不仅是效果层优化，也是推理降本手段。

## 8. 容量规划怎么做

### 8.1 不要只问“并发多少台”

生产容量不能只看“并发 200”这种单一数字，还要同时看：

- 是 `200 并发请求` 还是 `200 QPS`
- 平均输入 token
- 平均输出 token
- P95 延迟目标
- 峰值时长
- 是否命中 prefix cache
- 是否有轻量模型和规则分流

### 8.2 机器数的正确估算方式

容量估算应按下面思路做：

```text
所需实例数
= 峰值吞吐需求 / 单实例压测吞吐
再乘安全冗余系数
```

冗余系数通常至少要考虑：

- 灰度发布
- 机器故障
- 流量抖动
- 活动高峰

因此生产起步通常不是“压测刚好够就上线”，而是留出明显余量。

### 8.3 意图识别场景的经验判断

对于短输入、短输出、标签化返回的意图识别任务，单卡吞吐通常显著高于开放式生成任务。

这也是为什么：

- 意图识别场景更有机会使用 `INT8 / INT4`
- 更有机会从 `prefix cache` 中受益
- 更适合通过流量分层把 7B 使用率压到较低水平

## 9. 监控、灰度与回滚

### 9.1 监控指标

生产上至少需要监控：

- `QPS`
- `P50 / P95 / P99` 延迟
- `TTFT`
- 输入 token / 输出 token
- GPU 利用率
- GPU 显存占用
- 请求失败率
- 意图分类准确率
- 活动意图召回率
- 高价值 query 误判率
- 错误路由率

### 9.2 灰度策略

推荐灰度顺序：

1. 离线回放验证
2. 小流量影子测试
3. 1% 到 5% 灰度
4. 逐步扩大到主流量

灰度时不要只看系统指标，还要同步看业务指标，例如：

- 活动点击率
- 搜索零结果率
- 活动页导流率
- 新词命中率

### 9.3 回滚原则

必须提前准备好可回滚版本：

- `BF16` 基线版本
- `INT8` 版本
- `INT4` 版本
- 规则直返兜底版本

一旦出现以下情况，应快速回滚：

- 高价值 query 误判率飙升
- 活动流量错分明显
- P95 延迟持续超标
- GPU 显存异常抖动

## 10. 三种可落地的生产方案

### 方案 A：7B 直接在线主服务

适合：

- 业务还在快速迭代
- 尚未蒸馏到小模型
- 复杂 query 占比较高

建议：

- `merge + INT8 + vLLM`
- 规则和实时干预前置
- 输出严格结构化

这是最快可落地的方案，但不是长期最低成本方案。

### 方案 B：轻量模型主链路，7B 作为 fallback

适合：

- 意图识别是高频核心链路
- 请求量大
- 延迟要求严格

建议：

- 高频 query 用轻量模型主判定
- 新词和热点词由实时干预修正
- 低置信度 query 才进入 7B

这是更接近成熟生产系统的方案。

### 方案 C：7B 主要用于蒸馏和回流

适合：

- 线上对延迟和成本要求极高
- 意图空间相对稳定

建议：

- 7B 不承担主流量
- 主要用于生成标注样本、处理复杂 case、辅助迭代小模型

这是长期 TCO 最优的方向，但建设周期更长。

---

## 11. 最终建议

如果你们现在已经有了 `Qwen 7B + LoRA` 的成果，并且短期内确定要上线，我建议这样落地：

1. 单业务场景先 merge LoRA。
2. 用 `BF16 -> INT8 -> INT4` 做分阶段压测。
3. 第一版生产优先选 `INT8 + vLLM`，不要一上来激进上 `INT4`。
4. 把输出限制成固定标签或短 JSON。
5. 把实时干预层放到模型前后，优先吃掉新词和高确定性活动词。
6. 不要让 7B 扛全量流量，尽快补上规则层、轻量模型层和 fallback 路由。
7. 用离线回放、灰度、回滚机制保证上线安全。

一句话总结：

**对意图识别场景，真正生产级可用的方案，不是“把 LoRA 模型跑起来”，而是把 `模型服务、实时干预、流量分层、量化部署、监控灰度` 作为一个完整系统来设计。**
