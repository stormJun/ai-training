## 本讲目标

本讲主要围绕一个较大的演示项目展开，目标不是单纯讲解代码细节，而是帮助学习者建立三类能力：

1. 学会阅读较长的工程代码，尤其是业务系统或框架源码。
2. 理解工作流中的容错、降级、路由和统计是如何落到代码里的。
3. 认识规则系统、意图识别、槽位填充与记忆层在工作流编排中的工程位置。

讲师特别强调，这类代码并不只是教学示例，也来自真实工作场景中的降级与兜底设计，因此更适合作为“工程化阅读样本”。

## 一、长代码应该如何阅读

面对几百行甚至上千行代码时，最有效的方法不是逐行阅读，而是先找到“入口”和“主流程”。

### 1. 先找入口

如果是平台型系统或 Web 应用，入口通常是一个 HTTP URL，沿着对应的后端接口可以一路追踪到核心函数。如果是普通脚本或服务，则应先看主程序入口，例如 `main` 函数、初始化流程或启动逻辑。

### 2. 再看作者的组织思路

人工编写的代码通常会体现明确的抽象结构，而不是单纯按实现顺序堆叠。阅读时应优先识别：

- 初始化做了什么
- 单次处理逻辑在哪里
- 批量处理逻辑在哪里
- 统计、监控或日志逻辑在哪里

讲师给出的阅读顺序是：

`初始化 -> 单次处理 -> 批量处理 -> 统计`

其中，批量处理往往只是单次处理的扩展，因此先读清单次路径，再回头看批处理，效率更高。

### 3. 找关键功能对应的模块

如果目标是理解“重试”“降级”“统计”“路由”这类能力，就不需要平均分配注意力，而应直接定位负责该能力的模块或函数。例如：

- 想看重试机制，就找负责异常处理和 fallback 的模块
- 想看业务链路，就找 service 或 chain 的组装逻辑
- 想看统计能力，就找 metrics、logger 或聚合输出部分

## 二、演示项目的核心设计

这个示例项目的目标是构建一个具备多层兜底能力的客服或问答流程。用户不仅会提出问题，还会携带一定的业务数据。系统在处理时希望做到以下几点：

- 优先由轻量模型承接请求
- 如果主模型失败，能够自动降级
- 如果降级仍失败，具备最终兜底策略
- 处理流程中可以输出业务统计信息

从工程结构上看，这个系统一般会包含三个层面：

- 模型配置层
- 业务链配置层
- 容错与 fallback 层

讲师强调，真正值得重点看的不是业务提示词，而是“模型设置”“链路组装”“异常处理”这三块。

## 三、工作流中的容错与降级

### 1. 主模型与备用模型

一个典型的工作流系统不会只依赖单一模型，而是会设置：

- 主模型
- 备用模型

主模型负责正常路径，备用模型负责故障时接管。真实业务里，备用模型可能是：

- 同一家供应商的低一级模型
- 不同供应商提供的同级模型
- 价格更低、质量略弱但稳定性更高的模型

### 2. 用异常处理替代复杂条件判断

讲师特别强调，容错逻辑不必通过大量 `if/else` 来组织，很多时候直接使用异常处理会更清晰。

推荐模式是：

1. 优先调用主模型
2. 如果失败，主动抛出异常
3. 在 `try/except` 中捕获异常
4. 记录日志和告警
5. 切换到备用模型
6. 如果仍然失败，再进入最终兜底逻辑

这种写法的优点在于：

- 逻辑路径清晰
- 分支数量更少
- 便于扩展多级 fallback
- 日志和告警位置集中

### 3. 重试机制的角色

重试机制适合处理暂时性问题，例如：

- 网络抖动
- 模型服务偶发超时
- 临时不可用

但重试并不是万能的。如果达到最大重试次数仍然失败，就应尽快进入降级或人工兜底，而不是无限重试。

## 四、路由与业务分发

在工作流编排中，路由负责把不同类型的问题送入不同处理逻辑。讲师更推荐使用“映射表”或“字典路由”，而不是硬编码的多层分支。

典型做法是先完成意图识别，再通过“意图 -> 处理函数”的映射找到对应逻辑。例如：

- 查询订单 -> 查询订单处理器
- 售前咨询 -> 售前知识库链路
- 售后问题 -> 售后知识库链路

这种方式的好处是：

- 易于维护
- 易于扩展
- 可读性强
- 能把业务规则和执行函数解耦

## 五、规则系统在工作流中的价值

虽然课程主题与大模型有关，但讲师反复强调：规则系统仍然是大量业务工作流的基础设施，尤其在高吞吐、强约束场景中非常有效。

典型场景包括：

- 订单查询
- 物流状态查询
- 电信运营商客服
- 标准化售前售后问答

这些场景的共同特点是：

- 问题范围相对固定
- 结果路径可预测
- 性能要求高
- 错误代价较高

### 1. 规则工作流的基本结构

讲师建议把规则能力拆成独立模块，常见结构包括：

- `core/`：规则引擎核心逻辑
- `config/`：关键词、正则、配置文件
- `workflow/`：状态流转逻辑
- `slot_filler/`：槽位填充逻辑

这样设计的目的，是让业务人员也可以参与维护关键词和正则，而不必直接修改主程序。

### 2. 规则识别的常见策略

常见策略包括：

- 正则表达式
- 关键词匹配
- 状态机

推荐做法不是三选一，而是并行执行后再融合结果：

`预处理 -> 正则/关键词/状态机并行识别 -> 结果融合 -> 槽位填充 -> 路由到具体处理函数`

### 3. 槽位填充

槽位填充的目的，是从用户输入中抽取出下游程序真正需要的参数。例如：

用户说：“帮我查一下订单 123456 的状态。”

系统需要提取出的结构化信息可能是：

- 意图：查询订单
- 槽位 `order_id`：`123456`

一旦完成结构化提取，后续处理程序就不必再理解自然语言，而是直接消费槽位数据。

## 六、基于大模型的意图识别与实体提取

当规则无法覆盖全部情况时，就需要引入大模型或更广义的机器学习方法。

### 1. 大模型适合处理什么问题

适合交给大模型的场景通常包括：

- 意图表达非常灵活
- 规则难以穷举
- 需要抽取复杂实体
- 需要一定语义理解能力

不适合完全依赖大模型的场景则包括：

- 明确、固定、可规则化的问题
- 高并发、高频次、对成本敏感的路由任务

更合理的方案通常是：

`规则优先 -> 大模型兜底`

### 2. 命名实体识别与槽位填充

在电商、客服、票务等领域，用户问题往往包含许多关键实体，例如：

- 商品名称
- 品牌
- 材质
- 款式
- 订单号
- 地点
- 时间

大模型或 NER 模型的作用，是先把这些信息提取出来，再写入槽位。这样后续的工作流节点就可以基于结构化字段执行。

### 3. 基于 LangChain 的路由链

在课程示例中，讲师提到可以通过多提示词路由链，把用户问题先分流为：

- 售前问题
- 售后问题
- 其他问题

再分别交给对应知识库或处理链路。这类机制在 LangChain 中已有现成封装，但当场景稍复杂时，最终往往还是会迁移到更强的工作流框架。

## 七、记忆层与知识库的区别

讲师专门花了较大篇幅解释“记忆”和“知识库”的区别。

### 1. 知识库是静态的

知识库通常是预先整理好的文档、FAQ、图谱或数据库内容。它的特点是：

- 事先存在
- 较稳定
- 通常通过检索方式访问

### 2. 记忆是动态积累的

记忆来自交互过程本身。它会随着对话持续积累，目标是让系统能够：

- 记住用户之前说过什么
- 保持多轮对话连续性
- 避免前后矛盾
- 在跨 session 的情况下延续部分上下文

### 3. 记忆的价值

记忆最大的价值不在于“多存信息”，而在于“维持一致性与连续性”。如果没有记忆：

- 关闭会话后无法延续语境
- 长对话容易前后冲突
- 个性化回答难以持续生效

## 八、记忆的分类与操作

### 1. 按时间划分

最常见的划分方式是：

- 短期记忆
- 长期记忆

短期记忆服务于当前会话，主要解决上下文窗口有限的问题。长期记忆则更偏向用户偏好、习惯、长期事实和持久经验。

### 2. 按内容划分

除了时间维度，也可以按内容划分，例如：

- 情景记忆：过往互动经历
- 语义记忆：概念性知识与事实
- 技能记忆：做事方式、偏好和经验

### 3. 记忆的基本操作

记忆系统至少包含这些动作：

- 编码
- 存储
- 提取
- 压缩或总结
- 巩固
- 遗忘

其中“编码”非常关键。原始文本不能无差别直接存入记忆层，否则后续提取与复用效率会很低。系统通常需要先把内容转换成更适合存储和检索的形式。

### 4. 巩固与遗忘

如果某段对话在业务上很重要，可以把短期记忆总结后写入 Redis、数据库或专用记忆系统，转成长效记忆。

但并不是所有记忆都应该永远保留。系统还需要支持遗忘机制，否则记忆会不断污染当前任务。遗忘可以是：

- 显式删除
- 重要性衰减
- 时间衰减
- 上下文替换

## 九、LangChain 中的常见记忆方案

讲师提到的几种常见方案包括：

- `ConversationBufferMemory`
- `ConversationBufferWindowMemory`
- 基于 Redis 的持久化记忆
- `Memory0`

### 1. Buffer Memory

`ConversationBufferMemory` 适合快速实验，直接把对话历史保存在内存中，接入简单，但不适合长时间运行或高并发场景。

### 2. Window Memory

`ConversationBufferWindowMemory` 只保留固定轮数的上下文，适合控制窗口大小。它本质上是“滑动窗口”式的短期记忆。

### 3. Redis 持久化

Redis 适合做外部持久化记忆，便于跨会话、跨实例共享状态，但需要自己设计读写策略和生命周期管理。

### 4. Memory0

`Memory0` 是更贴近 AI 记忆层概念的方案。它不仅提供持久化能力，也更强调对话记忆的组织、总结和复用，适合后续进一步研究。

## 十、工程建议

讲师在本讲中反复强调几条实践建议：

- 长代码先找入口，再找主流程，不要平均阅读。
- 工作流中优先区分“固定路径”和“动态路径”。
- 规则系统不是落后方案，而是高可靠业务的重要基石。
- 大模型应优先承担兜底、消歧和复杂抽取，而不是替代所有逻辑。
- 记忆不是把所有历史原样塞回上下文，而是要做编码、总结与治理。

## 总结

这份文稿的核心价值，不在于某一段具体代码，而在于给出了一个比较完整的工程视角：

- 如何阅读工作流代码
- 如何设计容错和降级
- 如何在规则与大模型之间做分工
- 如何用槽位和路由把自然语言转成可执行流程
- 如何理解记忆层在 Agent 系统中的位置

如果把本讲当作一份“工作流工程化导论”，它讨论的重点不是单一框架 API，而是框架背后的设计方法。
