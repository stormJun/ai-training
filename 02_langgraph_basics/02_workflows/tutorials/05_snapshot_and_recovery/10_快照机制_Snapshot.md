# 快照机制（Snapshot）

这一节主要讲 LangGraph 里的快照、状态历史和恢复执行。

如果前面的工作流示例让你理解了“图是怎么跑的”，那么这一节要解决的是：

> 图跑过之后，状态能不能被保存下来？后面能不能从中间某一步继续？

这正是快照机制的意义。

---

## 这一节讲什么

这一份材料实际上包含了 3 类示例：

1. 最小快照示例
   演示 `checkpointer` 与 `get_state_history(...)`
2. 输入校验与重试示例
   演示状态历史如何帮助我们理解失败与重试过程
3. 模型降级示例
   演示把“主模型失败、备用模型接管”的过程也放进带快照的图里

所以这节不只是讲“保存状态”，也在讲：

> 为什么状态历史对于调试、恢复和容错都很重要。

---

## 什么是快照

在 LangGraph 里，快照可以理解成：

- 某个线程在某个执行时刻的状态记录

你可以把它想象成“工作流运行过程中的存档点”。

如果图启用了 `checkpointer`，那么在每一步执行之后，LangGraph 都可以把状态保存下来，之后你就能：

- 查看完整状态历史
- 拿到某个检查点
- 从指定检查点继续运行

这意味着图执行不再只是“一次性函数调用”，而更像一个可追踪、可恢复的状态机。

---

## 第一部分：最小快照示例

第一段示例是最干净的一版。

它做的事情很简单：

- 定义一个 `AgentState`
- 让图按 `node1 -> node2` 顺序执行
- 用 `MemorySaver()` 开启快照
- 用 `get_state_history(config)` 查看状态历史

核心点在这里：

```python
memory = MemorySaver()
graph = builder.compile(checkpointer=memory)
```

没有 `checkpointer`，图当然也能跑；但只有传了 `checkpointer`，你才能在后面拿到状态历史和检查点。

执行时再配一个 `thread_id`：

```python
config = {"configurable": {"thread_id": "123"}}
```

这个 `thread_id` 表示：

- 这次执行属于哪条线程
- 后续取状态历史时要按哪个线程来查

跑完之后，你就可以看到：

- 当前最终输出
- 从初始输入到最终结束之间的每一步 `StateSnapshot`

这一步的重点是建立一个概念：

> LangGraph 可以记住“图是怎么一步一步走到现在的”。

---

## 第二部分：从指定检查点恢复

当你已经拿到状态历史之后，下一步自然就是：

> 能不能回到其中某个时刻，再从那里继续？

示例里保留了这段操作：

```python
config = {
    "configurable": {
        "thread_id": "123",
        "checkpoint_id": "...",
    }
}

checkpoint_snapshot = graph.get_state(config)
graph.invoke(..., config=config)
```

这里的意思是：

- 通过 `checkpoint_id` 指定一个历史状态
- 用 `get_state(...)` 取回那个状态
- 再基于这个状态重新继续执行

从工程角度看，这种能力很有价值，因为它支持：

- 从中间状态恢复
- 调试某一步之后的行为
- 对比不同恢复路径的结果

---

## 第三部分：带输入校验的状态历史

第二段示例把快照和“输入错误重试”放在一起。

这里图的核心逻辑是：

1. 判断输入是不是合法订单号
2. 如果合法，就查询订单
3. 如果不合法，就进入错误处理
4. 最多重试 2 次

它保留快照的意义在于：

- 你可以回看每一步状态
- 看到 `retry_count` 是怎么变化的
- 看到消息列表是怎么逐步累积的

这比只看最终输出更适合排查问题，因为你能知道：

- 哪一步把状态改坏了
- 条件路由为什么走到了某个分支
- 重试次数是如何累计出来的

所以这一段想说明的是：

> 快照不仅是为了恢复，也是为了调试工作流内部状态变化。

---

## 第四部分：模型降级与快照

最后一段示例演示的是一种常见工程问题：

- 主模型调用失败
- 备用模型接管
- 最终仍然返回可用结果

它的核心思路是：

1. 先尝试主模型
2. 如果失败，切换到备用模型
3. 把真正使用的模型名写回状态

这里快照有两个好处：

- 你可以回溯模型切换前后的状态
- 你可以明确知道最终输出到底来自哪个模型

示例里还专门把 `current_model` 放进状态里，就是为了把这种“运行期决策结果”保存下来。

---

## 这一节真正要学的点

- `checkpointer` 是快照能力的入口
- `thread_id` 用来区分不同执行线程
- `get_state_history(...)` 可以查看完整状态演化过程
- `checkpoint_id` 可以把图拉回某个历史状态
- 快照不仅对恢复有用，对调试和容错同样重要

## 小结

这一节的核心不是“又多了一个 API”，而是视角发生了变化：

- 以前我们关心图能不能跑完
- 现在我们开始关心图在运行过程中的每一步状态

一旦你进入工程化阶段，这种能力会非常重要，因为很多问题都不是“最终结果错了”，而是：

> 某一步状态已经偏了，只是你之前看不见。

快照机制，就是让这些过程变得可见、可查、可恢复。
