# 工作流编排：讲师笔记整理版

> 基于原始转写稿 `03_工作流编排_讲师笔记.txt` 整理。
> 这份文档更像结构化课堂笔记，重点不是复现课堂语气，而是把概念、选型和实现路径整理清楚。

## 本讲目标

本讲承接前面的工具调用、记忆与意图识别内容，重点回答两个问题：

1. 如何把“思考、工具、记忆、路由”整合成一个真正能执行任务的 Agent。
2. 为什么在复杂场景中，需要从 LangChain 过渡到 LangGraph。

因此，本讲前半部分聚焦 ReAct 与工具调用，后半部分聚焦 LangGraph 的状态化工作流编排。

## 一、Agent 的基本闭环

讲师把 Agent 的工作过程概括为三个动作：

- 感知
- 决策
- 执行

感知负责理解用户任务，决策负责拆分步骤与选择工具，执行负责真正运行函数、模型或外部系统。更复杂的 Agent 还会形成闭环：

`感知 -> 决策 -> 执行 -> 再次感知 -> 再次决策`

如果问题一次没有解决，系统就继续下一轮推理和行动，直到得到结果或达到终止条件。

## 二、ReAct：让系统“会行动起来”

### 1. ReAct 的核心思想

ReAct 不是某个具体框架，而是一种组织推理与行动的模式。它把大模型的工作拆成循环结构：

`Thought -> Action -> Observation -> Answer`

如果问题尚未解决，就继续：

`Thought -> Action -> Observation`

直到模型确认自己有足够信息给出最终答案。

### 2. ReAct 适合什么问题

ReAct 更适合：

- 创作型任务
- 调研型任务
- 多步搜索与分析
- 路径依赖当前结果的任务

这类任务的特点是：下一步要做什么，往往取决于上一步拿到了什么结果，因此不适合提前写死流程。

### 3. ReAct 的驱动方式

ReAct 的核心不是流程图，而是提示词。提示词负责约束模型：

- 先思考
- 再决定是否调用工具
- 再观察工具结果
- 最后生成回复

因此，它本质上是一种“提示词驱动的动态执行模式”。

## 三、LangChain 中的 ReAct 实现

### 1. 基本三要素

讲师提到，使用 LangChain 构建 ReAct Agent 时，最核心的输入通常有三类：

- 模型
- 工具
- Prompt

只要这三部分齐备，就可以通过 `create_react_agent` 一类接口快速构建一个最小可运行的 Agent。

### 2. 模板与内置能力

LangChain 已经提供了默认的 ReAct Prompt 模板，开发者既可以直接复用，也可以根据业务做二次调整。对于快速验证来说，使用内置模板通常已经足够。

### 3. 示例场景

课程中举了一个物流场景的例子，工具虽然是 mock 的，但结构与真实系统一致。Agent 需要根据用户问题选择工具，例如：

- 查询包裹状态
- 计算运费
- 查询库存

这个例子说明，ReAct 并不要求工具一定来自真实接口，mock 工具同样可以用来验证工作流与推理路径。

## 四、工具调用的工程实践

### 1. 工具有两类来源

LangChain 中的工具大体可以分为两类：

- 框架内置工具
- 自定义工具

内置工具适合快速实验，例如搜索工具、网页访问工具等。自定义工具适合承接企业内部 API、数据库、业务服务和规则系统。

### 2. 自定义工具的常见写法

讲师介绍了用装饰器声明工具的方式。核心要点在于：

- 工具需要暴露清晰名称
- 工具需要暴露说明文字
- 工具需要明确输入参数

这些元信息都会被模型拿来判断“是否调用”“如何调用”。

### 3. 错误处理也必须进入工作流

工具调用失败时，不应让模型自行编造答案。更合理的做法是把错误显式暴露给 Agent，让模型知道当前调用失败，从而：

- 更换策略
- 告知用户失败
- 进入 fallback 路径

这比“返回一个看似正常但实际上错误的结果”更安全。

## 五、为什么需要 LangGraph

讲师给出的原因非常明确：随着 Agent 任务变复杂，LangChain 的线性链式写法会越来越难维护，主要体现在三个方面：

- 多轮对话难管理
- 状态传递难组织
- 工作流一复杂，代码量暴增

LangGraph 的意义，就是把这些问题上升为一套显式的工作流抽象。

## 六、LangGraph 的三个核心概念

LangGraph 可以抽象为三部分：

- 节点（Node）
- 边（Edge）
- 状态（State）

### 1. 节点

节点代表一个可执行步骤，本质上通常是一个函数，也可以是一个可调用类。节点负责：

- 读取状态
- 执行业务逻辑
- 返回状态更新

节点中可以封装的内容包括：

- 大模型调用
- 工具调用
- 普通业务逻辑
- 子图

### 2. 边

边负责描述节点之间如何流转。最常见的两类边是：

- 普通边
- 条件边

普通边表示固定顺序执行，条件边表示根据判断结果进入不同节点。

### 3. 状态

状态是图运行时共享的数据结构。所有节点围绕状态工作：

- 从状态中读取输入
- 对状态做局部修改
- 把新状态交给后续节点

状态相当于整个图的“上下文容器”。

## 七、State 的设计要点

### 1. 先设计状态，再设计图

讲师特别强调：写 LangGraph 时，往往不是先写函数，而是先定义状态 Schema。因为只有先明确整张图中哪些信息需要流动，节点和边的设计才会清晰。

### 2. `TypedDict` 与 `Pydantic`

课程中介绍了两种常见状态定义方式：

- `TypedDict`
- `Pydantic BaseModel`

它们都可以约束字段类型，但使用侧重点略有不同。一般来说：

- `TypedDict` 更轻量
- `Pydantic` 更严格，能力也更强

### 3. Reducer 与状态更新

有些状态字段适合覆盖更新，有些适合追加更新。例如消息列表通常就适合追加，而最终答案更适合覆盖。

因此，设计状态时不仅要定义字段，还要思考字段的更新行为。

## 八、边的几种常见模式

LangGraph 中常见的边模式包括：

- `START -> 节点`
- `节点 A -> 节点 B`
- 条件入口边
- 条件分支边
- `节点 -> END`

对于简单流程，可以直接用普通边串起来。对于需要判断登录态、任务类型、重试条件或结果质量的场景，则应使用条件边。

## 九、进阶能力：子图、检查点与人机协同

### 1. 子图

子图可以理解为“图中的图”。它适合：

- 复用一段复杂子流程
- 组织多 Agent 协作
- 把大图拆成更稳定的小模块

### 2. 检查点与快照

当图运行到一半被打断时，检查点机制可以保存当前状态，以便稍后继续执行，而不是从头再来。

这类能力非常适合：

- 人工审批
- 人机协同
- 长流程任务
- 可中断恢复场景

### 3. 人机协同

如果业务上必须等待人工确认，例如退款金额超过阈值、审批条件不足、结果需要人工审核，就可以在图中人为设置中断点，待人工输入后再继续恢复执行。

## 十、LangGraph 中的 ReAct 与 RAG

课程里展示了一个将 LangGraph 与 RAG 结合的例子。核心思路是：

1. 先判断问题更适合走向量检索还是 Web 搜索
2. 获取候选文档
3. 对文档做评分
4. 进入生成节点
5. 如果结果不理想，则重试或改走其他路径

这个例子的价值不在于“唯一正确实现”，而在于它把 LangGraph 的多个能力集中演示出来，包括：

- 条件入口
- 条件边
- 状态更新
- 循环重试
- 节点拆分
- 检索与生成协同

## 十一、ReAct 与有限状态机的边界

这是整讲里非常重要的一个判断标准。

### 1. 适合状态机的场景

如果路径固定、步骤顺序明确、节点之间关系不会动态变化，那么更适合使用有限状态机或显式工作流。例如：

- 审批流
- 固定流程客服
- 表单提交流程
- 订单状态流转

### 2. 适合 ReAct 的场景

如果路径依赖于实时搜索结果、创作过程或当前观察结果，那么更适合 ReAct。例如：

- 长文写作
- 调研分析
- 复杂问题求解
- 动态工具选择

一句话概括：

- 路径固定，用状态机或显式图
- 路径动态，用 ReAct

## 十二、LangChain、LangGraph 与平台产品如何选型

讲师给出了一个非常实用的“漏斗式选型”思路。

### 1. 平台优先

如果 Coze、Dify 之类平台已经可以覆盖业务需求的 80% 到 90%，就优先使用平台。理由很简单：

- 上线快
- 维护成本低
- 集成成本低

### 2. 平台不够，再看二开或插件

如果平台总体可用，但某个能力较弱，例如：

- 文档检索
- 切分策略
- 解析质量

那么优先考虑：

- 插件扩展
- 外部服务回填
- 局部二次开发

### 3. 平台整体不适配，再考虑 LangGraph 自研

如果需要大改整体逻辑，或者存在：

- 强合规
- 私有化
- 商业授权
- 深度定制流程

那么就应该考虑使用 LangGraph 自行搭建工作流系统，而不是继续在平台上做高成本改造。

## 十三、学习建议

讲师对 LangGraph 的学习顺序也给出了明确建议：

1. 先照着示例仿写简单图
2. 再自己重写 State、Node、Edge
3. 再从单节点图扩展到多节点图
4. 最后再逐步加入分支、重试、人工打断、RAG、ReAct 等高级能力

不建议一开始就直接写复杂多分支大图，因为这样很容易在状态设计和节点连接上同时失控。

## 总结

这份笔记的重点不只是介绍 LangGraph 的 API，而是建立一套判断框架：

- Agent 何时需要闭环
- ReAct 与工作流各适合什么问题
- LangChain 的边界在哪里
- LangGraph 为什么适合复杂编排
- 平台产品、插件增强与自研框架应如何分层选型

如果把本讲浓缩成一句话，可以表述为：

**LangChain 更适合组件级能力拼装，LangGraph 更适合把这些能力放进显式的、可恢复的、可分支的工作流系统中。**
