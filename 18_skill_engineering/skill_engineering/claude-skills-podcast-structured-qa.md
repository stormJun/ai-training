# Claude Skills 结构化问答整理

这份文档把原始讨论内容整理成更清晰的问答形式，并按主题分组。

整理原则：

- 尽量保留原始问答内容
- 只做结构化重排，不改动核心意思
- 将零散讨论合并到更容易复习的大类下面

## 一、主题说明

**Q：这份内容主要讲什么？**

A：这一期主要讲的是，怎么给 Claude 写高效的技能，包括：

- 怎么设计技能的结构
- 怎么做测试和迭代
- 怎么使用最佳实践
- 怎么让 Claude 更好地发现和使用这些技能

整体目标是提升 AI 的应用效率。

## 二、核心原则

**Q：在给 Claude 设计技能的时候，最基本要遵守的原则是什么？**

A：最重要的原则是简洁。因为上下文窗口是公共资源，不只是技能内容要占用它，系统提示、对话历史、其他技能的元数据、用户请求，都会共享同一个上下文窗口，所以每一个 token 都很宝贵。

**Q：为什么说简洁这么重要？**

A：因为启动的时候虽然只预加载了技能的名字和描述，但一旦技能被激活，`SKILL.md` 里的正文内容就会和对话历史一起竞争上下文空间。你写得越精简，就越不会挤占其他重要信息。

**Q：还有什么核心原则？**

A：另一个关键原则是，默认 Claude 已经很聪明了。不要去解释它本来就知道的东西，只需要提供它默认不知道、但完成任务又必须知道的背景信息。

**Q：在具体写技能时，怎么把握“默认 Claude 已经很聪明”这个原则？**

A：每写一句都问自己几个问题：

- Claude 真的需要这句话吗？
- 这个信息能不能默认它已经知道？
- 这一段的 token 成本值不值得？

**Q：能不能举个例子说明什么叫“太啰嗦”？**

A：可以。像 PDF 或图书馆系统这种常识性概念，如果技能里还花很多篇幅去解释，就会很浪费。好的版本会直接默认 Claude 已经理解这些概念，只写任务所需的额外信息。啰嗦版本的 token 可能是简洁版本的三倍，但并没有带来更多价值。

## 三、自由度设计

**Q：在设计技能的时候，怎么判断是应该给 AI 更高的自由度，还是严格限制它的操作？**

A：这取决于任务本身。

- 如果任务有很多种解决方法，需要根据现场情况灵活判断，那就适合高自由度，用文本方式描述原则和目标即可。
- 如果任务有固定套路，但又需要一定配置空间，那可以用伪代码或者带参数的脚本。
- 如果任务非常容易出错，或者步骤顺序不能乱，那就应该用非常具体的脚本，并尽量减少参数，确保执行一致性。

**Q：能不能用一个生活化的比喻来说明这三种自由度？**

A：可以。

- 如果任务像走一片开阔平地，那只要告诉它大方向就可以，这是高自由度。
- 如果任务像走一座很窄的桥，两边还是悬崖，那就必须给非常精确的指令，这是低自由度。

**Q：哪些具体任务适合高自由度，哪些适合低自由度？**

A：

- 数据库迁移这类任务步骤严格、顺序敏感，所以更适合低自由度。
- 代码审查这类任务每个项目情况不同，判断空间大，所以更适合高自由度。

## 四、模型差异与测试适配

**Q：如果技能要在不同型号的 Claude 上跑，测试的时候要特别注意什么？**

A：因为不同模型能力不一样，所以一定要在目标模型上分别测试。

- Haiku 可能需要更多引导
- Sonnet 更在意技能是不是写得清晰、紧凑
- Opus 本身能力很强，解释太多反而可能适得其反

**Q：也就是说，一套指令不一定能适配所有模型？**

A：对。有时候需要针对不同模型特性做一些调整，至少也要写出一套能兼顾目标模型的说明方式。

## 五、YAML Frontmatter、命名与描述

**Q：SKILL.md 的 YAML frontmatter 里有哪些字段是必须要有的？**

A：必须有两个字段：

- `name`
- `description`

**Q：`name` 有什么格式要求？**

A：

- 不超过 64 个字符
- 只能包含小写字母、数字和短横线
- 不能带 XML 标签
- 不能使用 `anthropic`、`claude` 之类的保留字

**Q：`description` 有什么格式要求？**

A：

- 不超过 1024 个字符
- 不能有 XML 标签
- 要清楚说明技能是干什么的
- 要说明什么时候应该使用它

**Q：技能命名到底有什么讲究？**

A：最推荐的是动名词形式，也就是动词加 ing，比如：

- `processing-pdfs`
- `analyzing-spreadsheets`

这种命名能很直观地表达技能是干什么的，也让整个技能库风格一致。

**Q：除了动名词形式，还有哪些命名方式可以接受？**

A：还有两种：

- 名词短语，比如 `pdf-processing`
- action-oriented，比如 `process-pdfs`

**Q：命名时要避免什么？**

A：要避免：

- 模糊词，比如 `helper`、`utils`
- 过于宽泛的词，比如 `documents`、`data`、`files`
- 使用保留字，比如 `anthropic-helper`、`claude-tools`
- 技能库里命名风格混乱、不统一

**Q：为什么统一命名方式对技能库维护很重要？**

A：因为统一命名会让：

- 文档引用更清楚
- 团队沟通更直观
- 技能查找和整理更方便
- 技能库整体看起来更专业、更有条理

**Q：写 description 时有哪些常见错误要避免？**

A：最常见的是使用第一人称或第二人称，比如：

- `I can help you process Excel files`
- `You can use this to process Excel files`

这些都不合适，因为 description 最终会被注入系统提示，所以应该使用第三人称，直接描述技能能力，例如：

- `Processes Excel files and generates reports`

**Q：除了视角问题，description 还要注意什么？**

A：要尽可能具体，明确写出：

- 这个技能能做什么
- 什么场景下应该使用它

因为 Claude 需要根据 description 从很多 Skills 里选出合适的那个，所以 description 必须足够具体，但具体执行步骤还是要放在 `SKILL.md` 正文里。

**Q：有没有有效和无效 description 的对比例子？**

A：有。有效的描述通常会明确写出：

- 处理对象是什么
- 输出是什么
- 什么情况下该用它

无效的描述往往太模糊，既没说清楚能做什么，也没说清楚什么时候该触发。

## 六、文档结构与 Progressive Disclosure

**Q：什么是 progressive disclosure pattern？**

A：它的核心思想是，`SKILL.md` 本身相当于一个目录和总览，只放最核心的信息，然后在需要的时候再引导 Claude 去看更详细的参考文件。这样可以避免一开始给 AI 太多信息，造成上下文拥挤。

**Q：具体怎么做 progressive disclosure？**

A：

- 尽量把 `SKILL.md` 主体控制在 500 行以内
- 如果超过这个长度，就拆分成单独文件
- 利用文件结构和引用组织说明、代码、资源
- 让结构清晰易读

**Q：简单技能和复杂技能的文件结构分别应该是什么样？**

A：

- 简单技能：一个 `SKILL.md` 就够，里面包含元数据和操作说明
- 复杂技能：把表单定义、参考资料、示例等拆成单独文件，按需加载

**Q：文件引用结构上，有什么最佳实践？**

A：尽量避免深层嵌套引用。

不推荐这种结构：

- `SKILL.md -> A -> B -> C`

更推荐：

- `SKILL.md -> A`
- `SKILL.md -> B`
- `SKILL.md -> C`

也就是说，参考文件最好都直接从 `SKILL.md` 一级引用出去。

**Q：如果 reference file 很长怎么办？**

A：如果参考文件超过 100 行，最好在开头加 table of contents。这样即使 Claude 只做 partial read，也能先理解整体结构，再去找需要的信息。

**Q：如果一个技能涉及很多不同领域，文件结构怎么组织更高效？**

A：可以按 domain 来拆，比如：

- sales
- finance
- marketing

这样 Claude 只需要加载当前任务相关的上下文，而不用读很多无关信息，也能节省 token。

**Q：如果有一些高级内容或者不常用内容，希望只有需要时才加载，怎么做？**

A：主文档只保留核心步骤，遇到高级场景时再给链接，让 Claude 去读对应文件，比如：

- `read more about redlining`
- `read OOXML.md`

这样主文档能保持简洁，不常用信息也不会长期占用上下文。

## 七、Workflow、Checklist 与 Feedback Loops

**Q：在复杂任务里，怎么设计 workflow 才能让 AI 一步一步做对？**

A：要把复杂任务拆成非常清晰的步骤，一步一步写出来。对于特别复杂的流程，还可以提供 checklist，让 AI 把 checklist 带进输出里，每完成一步就打勾，这样既能看到整体进度，也不容易漏掉关键环节。

**Q：为什么 checklist 特别适合复杂任务？**

A：因为像 research synthesis、PDF form filling 这类任务：

- 步骤多
- 容易漏项
- 错误代价高

checklist 可以把整个任务显式化，让 Claude 按部就班执行。

**Q：什么是 feedback loop？**

A：feedback loop 的意思是让 AI 在生成内容之后，再根据 validator、style guide 或规则去检查自己的结果，如果发现问题再修正，一直迭代直到符合要求。

**Q：feedback loop 为什么能提升质量？**

A：因为它把一次性生成，变成了带校验的生成。这样可以：

- 提前发现错误
- 修正格式问题
- 提升输出稳定性
- 显著提高最终质量

**Q：实际操作中，feedback loop 可以怎么做？**

A：

- 用 style guide 检查格式
- 用 validation script 验证内容正确性
- 根据错误信息让 Claude 重新修正

## 八、内容维护与一致性

**Q：为什么技能里要尽量避免写会过期的信息？**

A：因为时间敏感信息会让技能很快失效，比如具体年份、日期、旧模式等。如果这些内容混在主流程里，就需要频繁维护。

**Q：如果一定要保留历史信息，怎么处理比较好？**

A：可以专门建一个 section，比如 `old patterns`，把历史信息放进去。这样既能提供上下文，又不会污染主流程。

**Q：为什么要坚持统一术语？**

A：因为如果同一个概念被不同词反复表达，比如：

- `API endpoint`
- `URL`
- `field`
- `box`

Claude 可能会把它们理解成不同的概念，从而产生误解和执行错误。术语一致性能显著提升执行可靠性。

## 九、常见设计模式

**Q：写 Skill 时有哪些常见设计模式？**

A：有几类特别常见：

- template pattern
- examples pattern
- conditional workflow pattern

**Q：template pattern 是什么？**

A：就是提前规定输出格式。

- 如果你需要非常严格的输出结构，比如 API response，就用严格模板
- 如果你只需要大致格式，就用较松的模板，让 Claude 有一定调整空间

**Q：examples pattern 是什么？**

A：就是给 input/output 示例，让 Claude 更容易抓住：

- 你想要的风格
- 你想要的 detail level
- 你想要的输出结构

这对复杂生成任务特别有帮助。

**Q：conditional workflow pattern 怎么用？**

A：对于有很多条件分支的流程，要把每个决策点写清楚。如果分支特别多，可以拆成单独文件，让 Claude 根据任务动态加载对应流程，这样逻辑更清晰，也更容易维护。

## 十、Evaluation 与 Iteration

**Q：为什么在开发技能之前，要先设计评估方案？**

A：因为只有先准备好评估场景，后面的开发才不会跑偏。你不是为了写文档而写文档，而是在解决真实存在的问题。

**Q：具体应该怎么做评估？**

A：

1. 先找出没有这个 Skill 时，Claude 会失败的真实任务
2. 针对这些痛点至少准备 3 个测试场景
3. 先在“没有 Skill”的情况下跑一遍，记录表现
4. 再写最少量的 instructions 去通过这些测试
5. 每轮迭代后重新比较是否有提升

**Q：评估表大概是什么结构？**

A：可以是一个简单表格，包含：

- input
- expected output
- actual output
- result（pass / fail）

必要时还可以补充评分标准，比如满足哪些条件才算 pass。

**Q：为什么这种评估表很重要？**

A：因为它是最客观的衡量依据，你可以清楚地看出这个 Skill 到底是不是在提升任务效果，而不是凭感觉判断。

## 十一、如何用 Claude 自己开发和优化 Skill

**Q：怎么利用 Claude 自己来帮助开发 Skill？**

A：可以用两个 Claude 实例。

- Claude A：负责写和优化 Skill
- Claude B：负责实际测试 Skill

**Q：Claude A 和 Claude B 分别怎么用？**

A：

先用 Claude A 手动完成一个完整任务，在这个过程中记录：

- 反复提供的上下文
- 常见偏好
- 反复强调的流程
- 需要额外补充的规则

任务完成后，让 Claude A 把这些内容整理成一个初步的 `SKILL.md`，包括 frontmatter 和主结构。

然后再让 Claude A 继续：

- 精简冗余内容
- 拆分 reference files
- 调整结构组织

接下来用一个新的 Claude B 实例加载这个 Skill，拿真实任务去测试它，观察：

- 它是否能找到正确的信息
- 是否会按预期执行
- 哪些地方会出错或困惑

然后把这些问题反馈给 Claude A，再继续修正。

**Q：如果是优化一个已经存在的 Skill，流程有什么不同？**

A：逻辑类似，但重点是观察 Claude B 的真实执行过程，仔细记录：

- 哪些步骤容易出错
- 哪些地方会犹豫
- 哪些步骤多余
- 哪些信息缺失

然后把这些问题连同当前 Skill 一起交给 Claude A，让它给出修改建议，再回到 Claude B 重新验证。

## 十二、团队反馈与真实使用观察

**Q：团队反馈在优化 Skill 里有什么作用？**

A：团队反馈能帮你发现你自己看不到的问题。把 Skill 给同事实际使用，然后观察：

- 该触发时是否能触发
- 大家能不能清楚理解这个 Skill 是做什么的
- 使用过程中有没有缺功能
- 有没有遗漏的场景

真实使用反馈能帮助你补上盲区。

**Q：除了团队反馈，还应该观察什么？**

A：还要观察 Claude 的真实读取行为，比如：

- 它会不会跳去你没预料到的文件
- 它读取文件的顺序是不是符合你的设计
- 某些文件是不是反复被读
- 某些文件是不是从来没被用到

这些都能反映出 Skill 的结构是否直观、description 是否足够精准。

## 十三、常见反模式

**Q：写 Skill 时有哪些常见反模式一定要避免？**

A：有几类特别常见：

### 1. 路径写法不兼容

比如用 Windows 风格反斜杠：

- `scripts\helper.py`

更推荐统一使用：

- `scripts/helper.py`

这样 Skill 才能在不同平台上兼容。

### 2. 给太多解决方案

如果一个 Skill 里罗列太多可选方案，AI 反而更容易犹豫。应该尽量聚焦到真正关键的步骤，而不是把所有可能性都堆进去。

### 3. 假设环境已经具备某些依赖

不能默认某个工具、某个库、某个包已经在环境里。依赖一定要明确写出来。

### 4. 结构设计想当然

不能只按自己的想象组织 Skill，而要根据 Claude 实际读取和执行的行为不断调整。

## 十四、Advanced：可执行代码与工程实践

**Q：如果 Skill 里包含可执行代码，最重要的注意事项是什么？**

A：最核心的是：

- 错误处理
- 参数说明
- 验证机制

要尽量在脚本里处理各种错误，而不是把问题抛给 AI 去猜。

**Q：错误处理为什么这么重要？**

A：因为如果脚本只返回一个模糊失败，Claude 不知道发生了什么，就没法采取正确行动。比如数据库连接失败时，要明确告诉它：

- 是超时
- 是权限不足
- 还是连接地址错误

这样 AI 才知道下一步该怎么处理。

**Q：参数配置为什么也要特别注意？**

A：所有配置参数都要写清楚：

- 它的含义是什么
- 默认值是什么

不要在代码里留下看不懂的魔法值（voodoo constants），否则无论是人还是 AI，后续维护都会非常困难。

**Q：为什么推荐尽量使用 utility scripts？**

A：因为把常用功能封装成固定脚本，比让 AI 现场生成代码稳定得多。这样可以：

- 降低语法和逻辑错误
- 保证每次执行结果一致
- 降低上下文消耗
- 提高整体流程统一性

## 十五、视觉分析与 Plan-Validate-Execute

**Q：如果 Skill 处理 PDF 表单，怎么提高准确率？**

A：可以先用脚本，比如 `pdf_to_images.py`，把 PDF 转成图片，再让 Claude 分析图片。这样它能理解表单的布局和字段关系，提取和填写会比单纯靠文本解析更准确。

**Q：什么是 plan-validate-execute 模式？**

A：它的核心思路是：

1. 先让 AI 生成结构化执行计划，比如 JSON
2. 用脚本或验证器检查计划是否正确
3. 验证通过后才真正执行

**Q：为什么这个模式特别有用？**

A：因为它在真正执行前加了一层检查，尤其适合：

- 批量操作
- 复杂表单处理
- 高风险任务

这样可以提前发现问题，降低执行错误。

## 十六、依赖、环境与 MCP

**Q：如果 Skill 依赖外部 npm 包或 PyPI 库，要注意什么？**

A：要看运行环境。

- 在 claude.ai 这类环境里，通常可以联网安装 npm / PyPI 包，也能拉 GitHub 仓库
- 在 Claude API 某些环境里，不能联网，因此依赖必须提前准备好

**Q：所以写 `SKILL.md` 的时候，依赖要怎么写？**

A：一定要明确列出：

- 需要哪些包
- 需要哪些工具
- 哪些环境已经预装
- 哪些需要提前安装

不能让 Skill 在运行时因为缺依赖而报错。

**Q：Claude 的这个运行环境本身会影响 Skill 设计吗？**

A：会。因为它本质上是一个可以执行代码的环境，通常可以：

- 访问文件系统
- 运行 bash 命令
- 执行脚本

所以 Skill 设计时应该充分利用这些能力，把文件组织、脚本调用和资源管理都做清楚。

**Q：文件和目录结构为什么会影响 Claude 使用 Skill 的效率？**

A：因为 Claude 会像在一个文件系统里工作一样去定位资源。所以：

- 路径要统一用正斜杠
- 文件名要能反映内容
- 资源最好按领域组织

这样它才能高效找到需要的内容。

**Q：如果 Skill 用到 MCP 工具，有什么特别要注意的？**

A：要使用全限定名，也就是：

- `server_name:tool_name`

例如：

- `BigQuery:bigquery_schema`
- `GitHub:create_issue`

这样在多个 MCP server 共存时，Claude 才不会混淆。

## 十七、上线前检查清单

**Q：写完一个 Skill 之后，怎么系统检查它是否符合最佳实践？**

A：可以按 checklist 一项一项检查。

### 元数据检查

- description 是否具体
- 是否写清楚功能和适用场景
- name 是否规范

### 正文与结构检查

- `SKILL.md` 是否过长
- 是否已经拆分成参考文件
- 引用是否尽量只有一层
- 复杂流程是否拆成清晰步骤
- 是否存在时间敏感信息
- 术语是否一致

### 代码与工程检查

- 脚本是否足够健壮
- 错误处理是否明确
- 是否存在未解释的魔法值
- 依赖是否写清楚
- 路径是否跨平台兼容
- 关键步骤是否有验证

### 质量与测试检查

- 关键任务是否引入 feedback loop
- 是否至少有 3 个真实测试用例
- 是否在不同模型上跑过
- 是否经过团队成员实际试用
- 是否根据反馈做了最后调整
