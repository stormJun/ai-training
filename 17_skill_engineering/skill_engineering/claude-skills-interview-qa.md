# Claude Skills 面试问答

这份文档基于 Claude 官方文档 `Agent skills best practices` 进行整理，但表达方式改成了面试视角，重点回答“Skills 是什么、为什么需要、怎么设计、怎么评估、有哪些常见误区”。

参考来源：

- Claude Docs: Agent Skills Best Practices
- https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices

## 1. 什么是 Skill

**Q: 如果面试官问，什么是 Skill？**

可以这样回答：

“我理解的 Skill，本质上是给 Agent 提供的一种可复用能力封装。它不是单纯的一段提示词，而是把任务触发条件、能力边界、执行步骤、依赖资源和输出预期整理成一个独立单元。这样模型在合适的时候可以按需加载，而不是把所有规则都堆在主 prompt 里。”

补充说明：

- Skill 解决的是能力模块化问题
- 它适合承载特定领域知识、固定工作流、工具使用规范
- 它的价值在于复用、可维护、可迭代，而不是只为了“多写一份 prompt”

## 2. 为什么需要 Skills，而不是把所有内容都写进 System Prompt

**Q: 为什么 Skills 比把所有说明塞进 system prompt 更好？**

可以这样回答：

“因为所有内容都放进 system prompt 会带来两个问题：第一是上下文臃肿，第二是能力边界不清。Skills 的思路是按需加载，只有在任务匹配时才把相关知识和流程引入上下文，这样既能控制 token 成本，也能让 Agent 在复杂场景下更稳定。”

可以进一步补一句：

“从工程角度看，Skills 也是一种 prompt modularization。它让能力可以单独维护、单独测试、单独迭代，这比维护一份越来越长的总提示词更可控。”

## 3. 一个好的 Skill 应该具备哪些特征

**Q: 你认为什么样的 Skill 才算设计得好？**

面试里可以答：

“一个好的 Skill 至少要满足四点：触发条件清晰、内容足够聚焦、执行步骤明确、加载成本可控。也就是说，模型要知道什么时候该用它，用了以后应该怎么做，而且不要因为一个 Skill 把大量无关内容带进上下文。”

展开来说：

- 触发条件清晰：模型能判断什么时候调用
- 作用范围清晰：它解决什么，不解决什么
- 步骤明确：执行顺序和关键动作不能模糊
- 信息密度高：只保留必要知识，避免冗长背景描述

## 4. Skill 的 description 应该怎么写

**Q: Skill 的描述字段为什么重要？应该怎么写？**

可以这样回答：

“Description 本质上是模型做路由决策的入口。它不只是给人看，更是给模型判断‘这个 skill 什么时候该被触发’用的。所以 description 不能写得太泛，也不能太空，要明确任务类型、典型触发词和使用场景。”

好的 description 通常应该包含：

- 适用任务
- 典型场景
- 能解决的问题类型
- 不适用的边界

一个关键点是：

“Skill 的入口写得越模糊，误触发和漏触发就越多。”

## 5. Skill 内容应该长还是短

**Q: Skill 是不是越详细越好？**

更好的回答是：

“不是。Skill 不是越长越好，而是越有效越好。官方最佳实践强调信息要高密度、尽量简洁。因为 Skill 被加载到上下文里，本质上是在消耗模型注意力，所以应该优先保留那些真正能影响决策和执行的内容。”

你可以补充一句：

“如果一段信息不会改变模型行为，那它大概率就不应该放进 Skill。”

## 6. Skill 里应该写背景知识，还是写执行步骤

**Q: Skill 设计时，更重要的是知识还是流程？**

推荐回答：

“两者都需要，但一般优先保证流程清晰。因为很多任务失败，不是模型缺知识，而是不知道应该按什么顺序做。好的 Skill 通常会同时提供必要背景和明确步骤，但重点会放在‘先做什么、再做什么、什么情况下停止或切换策略’。”

换句话说：

- 知识告诉模型“知道什么”
- 流程告诉模型“怎么做”

在工程场景里，后者通常更关键。

## 7. Skill 里的步骤应该写到什么程度

**Q: 执行步骤是不是要写得非常细？**

可以这样回答：

“步骤要足够明确，但不应该机械到把模型变成流程脚本。最佳实践更偏向在关键节点给出明确约束，比如先检查前置条件、再执行核心动作、最后验证结果；而不是把所有微小动作都展开，否则会让 Skill 冗长且脆弱。”

面试里可以总结成一句：

“Skill 需要的是可执行性，不是流水账。”

## 8. 什么时候适合做成 Skill

**Q: 什么样的内容适合抽成 Skill？**

可以这样回答：

“我通常会在三种情况下抽 Skill。第一，这个任务会反复出现；第二，它有稳定的执行模式；第三，执行效果明显依赖特定知识或特定流程。如果一个能力既常用、又容易做错、还值得长期维护，那它就很适合做成 Skill。”

常见适用类型：

- 固定工作流
- 特定工具链使用方法
- 领域知识总结
- 复杂任务的操作规范
- 需要高一致性的交付流程

## 9. 什么时候不适合做成 Skill

**Q: 哪些内容不应该做成 Skill？**

可以这样回答：

“如果内容只会用一次、边界还没稳定、或者本质上只是一些很零散的规则，那通常不适合立即抽成 Skill。因为 Skill 也是一种长期资产，维护成本是真实存在的。过早抽象会导致仓库里出现大量没人维护、也不稳定的 pseudo-skill。”

不适合的情况包括：

- 一次性任务
- 规则还在快速变化
- 只有少量零散提示
- 复用价值很弱

## 10. Skill 应该如何组织结构

**Q: 你会怎么组织一个 Skill 的结构？**

可以这样回答：

“我一般会把 Skill 组织成五部分：用途说明、触发条件、关键步骤、依赖资源、失败/边界处理。这样模型既知道为什么用，也知道什么时候用、怎么用、出了问题怎么办。”

一个实用结构可以是：

1. Skill 目标
2. 适用场景
3. 执行步骤
4. 注意事项和边界
5. 依赖文件、脚本或工具

## 11. Skill 为什么强调 progressive disclosure

**Q: 官方为什么强调 progressive disclosure，而不是一次性加载所有资料？**

可以这样回答：

“因为大模型的上下文虽然长，但注意力不是无限的。Progressive disclosure 的本质是分层加载：先给模型最小必要信息，只在需要时再打开更细的参考资料、脚本或模板。这样能降低噪声，提高命中率，也更节省 token。”

一句话理解：

“先给路由信息，再给执行信息，最后才给细节资料。”

## 12. Skill 和工具调用的关系是什么

**Q: Skill 和 tool 是什么关系？**

可以这样回答：

“我会把 Skill 理解成‘如何做’的知识和流程层，把 Tool 理解成‘做这件事的执行接口’。Skill 告诉模型什么时候该调用哪些工具、顺序是什么、参数怎么构造、结果怎么验证；Tool 则负责真正执行动作。两者是互补关系，不是替代关系。”

所以：

- Tool 是 capability endpoint
- Skill 是 capability orchestration guidance

## 13. Skill 怎么评估效果

**Q: Skill 做出来以后，你怎么判断它是否有效？**

可以这样回答：

“Skill 不能只看写得漂亮不漂亮，而要看是否提升了真实任务表现。评估时我会看三个层面：第一，触发是否准确；第二，执行路径是否稳定；第三，结果质量是否真的提升。最好能准备一组代表性任务，做前后对比测试。”

常见评估指标：

- 是否正确触发
- 是否减少误操作
- 是否提高回答/执行一致性
- 是否减少上下文浪费
- 是否提升成功率

## 14. Skill 的常见误区有哪些

**Q: 设计 Skill 时常见误区是什么？**

可以这样回答：

“我见过最常见的误区有四类。第一，description 写得太泛，导致模型不会触发；第二，内容过长，加载后全是噪声；第三，只写背景不写步骤，模型知道概念但不会执行；第四，缺少边界和失败策略，导致模型在不适用场景下也硬套这个 skill。”

可以压缩成一句：

“最常见的问题不是 Skill 不够多，而是 Skill 不够准、不够短、不够可执行。”

## 15. 如果让你总结 Claude Skills best practices，你会怎么说

**Q: 一句话总结 Claude Skills 的最佳实践？**

推荐回答：

“我的总结是，Skills 的核心不是‘多写一些提示词’，而是把高价值、可复用、可评估的能力沉淀成按需加载的模块。好的 Skill 一定是触发清晰、信息高密度、步骤可执行、边界明确、并且能通过真实任务持续迭代的。”

## 16. 面试收尾版回答

如果面试官问得比较宽泛，可以直接用下面这版：

“我理解 Claude Skills 本质上是一种面向 Agent 的能力模块化机制。它的作用不是把提示词写得更长，而是把特定任务所需的知识、流程和工具使用规范封装成独立能力单元，让模型在合适的时候按需加载。设计 Skill 时我会重点关注五件事：触发条件是否清晰、description 是否能帮助路由、内容是否足够聚焦、步骤是否可执行、以及是否有明确边界和评估方法。一个好的 Skill 不只是文档写得完整，而是真的能提升任务成功率和稳定性，同时又不会把无关信息带进上下文。” 

## 17. 复习提纲

如果要快速复习，可以只记下面这些关键词：

- Skill 是能力封装，不只是 prompt
- 按需加载优于全量塞进 system prompt
- description 决定触发质量
- 内容要高密度、低噪声
- 流程比背景更重要
- progressive disclosure 很关键
- Skill 管方法，Tool 管执行
- 最终要靠任务评估验证有效性

## 18. 设计 Skill 时最核心的原则是什么

**Q: 如果面试官问，设计 Claude Skill 最基本要遵守什么原则？**

可以这样回答：

“最核心的原则是简洁。因为上下文窗口是公共资源，Skill 内容、系统提示、历史对话、其他技能元数据和用户请求都要共享同一个上下文预算。Skill 一旦被激活，它的正文就会和其他信息竞争注意力，所以每一个 token 都应该有明确价值。”

补充一句会更完整：

“Skill 不是写得越多越好，而是应该只保留那些真正能改变模型行为的信息。”

## 19. 为什么说要默认 Claude 已经很聪明

**Q: 官方为什么强调默认模型已经很聪明？**

可以这样回答：

“因为 Skill 的任务不是重新教模型通识知识，而是补充那些它默认不知道、但执行这个任务必须知道的背景信息。如果你把模型本来就知道的概念重新解释一遍，只会浪费上下文，并不会提升效果。”

一个常用判断标准是：

- 这句话 Claude 真的不知道吗
- 这句话会改变它的执行决策吗
- 这段说明值得它占用上下文吗

## 20. Skill 里应该给模型多大自由度

**Q: 设计 Skill 时，怎么判断该给模型高自由度还是低自由度？**

可以这样回答：

“这取决于任务本身。如果任务有很多可能路径，需要根据现场信息灵活判断，那就应该给高自由度，用原则性的文本指导；如果任务步骤固定、顺序敏感、容易出错，那就应该给低自由度，用更明确的伪代码、参数化流程甚至固定脚本来限制执行方式。”

可以进一步拆成三类：

- 高自由度：任务开放，路径多，依赖判断
- 中自由度：主流程固定，但允许参数配置
- 低自由度：步骤严格、顺序敏感、容错低

## 21. 哪些任务适合高自由度，哪些适合低自由度

**Q: 能举例说明不同自由度的适用场景吗？**

可以这样回答：

“像代码审查、研究分析、需求拆解这类任务，通常适合高自由度，因为每个项目上下文不同；而数据库迁移、表单填写、批量修改配置这类任务，更适合低自由度，因为步骤一旦乱掉或者漏掉，后果会比较严重。”

面试里可以用一句比喻：

“如果任务像走一片开阔平地，只给方向就够了；如果任务像走一座窄桥，就必须给非常精确的动作指令。”

## 22. 不同模型下，Skill 要怎么适配

**Q: 如果 Skill 需要跑在不同型号的 Claude 上，应该注意什么？**

可以这样回答：

“不同模型的能力边界和偏好不一样，所以 Skill 最好在目标模型上分别验证。能力较弱的模型通常需要更清晰的步骤引导，而能力更强的模型更看重说明是否紧凑、结构是否清晰。如果用一套写法强行适配所有模型，往往会在某些模型上表现明显下降。”

更工程化一点的说法是：

“Skill 设计不能脱离 target model profile。你要针对目标模型做测试，而不是只在一个模型上验证成功就认为可泛化。”

## 23. YAML frontmatter 为什么重要

**Q: Skill 文件的 YAML frontmatter 有什么作用？**

可以这样回答：

“Frontmatter 是 Skill 的元数据入口，它决定模型怎么识别和路由这个 Skill。最关键的是 `name` 和 `description`，前者用于稳定标识，后者用于触发判断。如果这两部分写不好，后面的正文再优秀，Skill 也可能根本不会被正确发现。”

面试里可以补一句：

“正文决定 Skill 用得好不好，frontmatter 决定 Skill 能不能先被用上。”

## 24. Skill 命名有什么最佳实践

**Q: Skill 的命名应该遵循什么规范？**

可以这样回答：

“命名的核心目标是让人和模型一眼看出它是做什么的。最佳实践是使用一致的命名风格，优先采用明确表达动作或任务的名字，比如动名词形式或者动作导向短语，避免 helper、utils 这种模糊词，也避免 documents、data 这种太泛的词。”

常见推荐风格：

- 动名词：`processing-pdfs`
- 名词短语：`pdf-processing`
- 动作导向：`process-pdfs`

需要避免：

- `helper`
- `utils`
- `documents`
- `data`

## 25. description 常见错误有哪些

**Q: 写 Skill 的 description 时，最容易犯什么错？**

可以这样回答：

“最常见的错误有三个：第一，写得太模糊，导致模型不知道什么时候触发；第二，用第一人称或第二人称，而不是直接用第三人称描述能力；第三，只写功能，不写适用场景。description 的目标是帮助模型做路由，所以必须同时讲清楚‘能做什么’和‘什么时候该用’。”

一个实用原则是：

“description 要足够具体，但不要把具体执行步骤塞进去，步骤应该放在正文里。”

## 26. 为什么 Skill 正文最好控制长度

**Q: Skill 的正文为什么要控制长度，比如 500 行以内？**

可以这样回答：

“因为正文一旦被激活就进入上下文，过长的正文会让模型读不完、抓不住重点，也会挤压其他有价值的信息。把 Skill 主体控制在一个适中的规模，能保证它既有足够的操作性，又不会变成上下文负担。复杂 Skill 应该通过拆分参考文件来扩展，而不是把所有内容堆在一个主文件里。”

## 27. 复杂 Skill 的目录结构应该怎么设计

**Q: 如果一个 Skill 很复杂，涉及很多文件，结构应该怎么组织？**

可以这样回答：

“最佳实践是让 `SKILL.md` 做总览和路由入口，把大块参考资料、例子、脚本说明按主题拆分成独立文件，并且尽量采用一级引用结构。也就是说，主文件直接指向各个参考文件，避免 A 引 B、B 引 C 这种多层嵌套，因为那会让模型在按需读取时容易丢失结构感。”

可以补充几个组织原则：

- 主文件只保留核心流程
- 参考文件按主题或领域拆分
- 引用尽量一层直达
- 超长参考文件开头最好有目录

## 28. 什么是 progressive disclosure pattern

**Q: 在 Skill 设计里，progressive disclosure 到底是什么意思？**

可以这样回答：

“它的本质是分层暴露信息。主文件只告诉模型最小必要规则和执行入口，遇到特定问题时，再跳到相应的参考文件、脚本或模板。这样做可以让主文档始终保持高信噪比，同时保留复杂任务所需的深层信息。”

一句话概括：

“默认只给必要信息，遇到具体问题再展开。”

## 29. 为什么要统一术语

**Q: Skill 里为什么要特别强调术语一致性？**

可以这样回答：

“因为模型会把术语当成任务语义的一部分。如果同一个概念一会儿叫 endpoint，一会儿叫 URL，一会儿又叫 target，模型可能会错误地把它们当成不同对象，导致理解偏差或执行错误。统一术语本质上是在减少语义分叉。”

面试里可以直接说：

“一致性会直接提升 Skill 的可执行性。”

## 30. 为什么要避免时间敏感信息

**Q: Skill 里为什么不建议写太多会过期的信息？**

可以这样回答：

“因为时间敏感信息会让 Skill 快速失效，增加维护成本。比如具体年份、旧流程、阶段性策略，如果直接混进主流程里，过一段时间就会误导模型。更好的做法是把稳定原则和易变信息分开，把历史模式或旧方案放到单独章节，避免污染主路径。”

## 31. Skill 中常见的设计模式有哪些

**Q: Skill 里有哪些常见的设计模式？**

可以这样回答：

“常见模式包括 template pattern、examples pattern、conditional workflow pattern 和 checklist pattern。模板适合约束输出结构，示例适合传达风格和细节层级，条件流程适合有分支决策的任务，而 checklist 特别适合多步骤复杂任务，能有效减少漏项。”

你也可以补一句：

“模式的本质是把不稳定的自然语言执行，转化成更稳定的认知支架。”

## 32. 为什么 checklist 对复杂任务特别有用

**Q: 在复杂流程里，为什么 checklist 很重要？**

可以这样回答：

“因为 checklist 能把长链路任务显式化，让模型知道当前进行到哪一步，还剩哪些步骤没完成。对于研究综合、表单填写、批处理、发布流程这种容易漏步骤的任务，checklist 能明显降低遗漏率，也更方便人工检查和回放。”

## 33. 什么是 feedback loop，为什么重要

**Q: Skill 里的 feedback loop 是什么？**

可以这样回答：

“feedback loop 指的是让模型在输出之后再做一轮自检，比如根据 style guide、validator、规则清单或脚本结果来检查自己的输出，然后在必要时修正。它的价值在于把一次性生成，变成带校验的生成，从而提高稳定性和质量。”

一句话理解：

“先产出，再校验，再修正。”

## 34. Skill 应该怎么做评估和迭代

**Q: 如果你来开发一个 Skill，你会怎么做评估和迭代？**

可以这样回答：

“我会先准备真实任务样例，而不是先写文档。先找出没有 Skill 时模型会失败的场景，再设计至少几组测试用例，记录 input、expected output、actual output 和 pass/fail。然后只写最少量的指令去通过这些测试，每改一次都重新跑评估。这样 Skill 的迭代是围绕真实问题收敛，而不是围绕写作感觉优化。”

这里的关键点是：

- 先有测试场景
- 再写最小必要 Skill
- 每轮迭代都做对比

## 35. 可以怎么用两个 Claude 实例来开发 Skill

**Q: 如何利用 Claude 自己来帮助开发和测试 Skill？**

可以这样回答：

“一个很实用的方法是双实例协作。让 Claude A 负责根据你的任务过程沉淀 Skill，总结重复使用的上下文、偏好和流程；再让 Claude B 在一个相对干净的环境里实际使用这个 Skill，观察它会不会触发、执行是否稳定、哪里会误解。然后把这些问题反馈回 Claude A，再做下一轮迭代。”

这个方法的好处是：

- 写的人和用的人视角分离
- 更接近真实使用环境
- 更容易暴露结构和触发问题

## 36. 如何观察 Skill 的真实使用行为

**Q: Skill 上线后，应该观察哪些行为信号？**

可以这样回答：

“要重点看三个信号：第一，它是否在该触发的时候触发；第二，模型实际读取文件的路径和顺序是否符合预期；第三，它是否频繁跳到你没预想到的参考文件，或者完全忽略某些你以为很关键的文件。这些都能反映出 Skill 结构是不是直观，description 是不是精准，以及正文的导航是否有效。”

## 37. 常见反模式有哪些

**Q: Claude Skills 设计里，哪些反模式要尽量避免？**

可以这样回答：

“常见反模式包括：内容过长、信息重复、给太多备选方案、目录引用层级过深、术语不一致、依赖没有写清楚、把时间敏感信息写进主流程，以及假设运行环境中一定存在某个工具或包。这些问题都会降低 Skill 的稳定性和可维护性。”

再补一个工程细节：

“文件路径最好统一用正斜杠，而不是平台相关写法，否则跨平台执行会出问题。”

## 38. 为什么推荐用 utility scripts

**Q: 在 Skill 里，为什么推荐把一些能力做成 utility scripts？**

可以这样回答：

“因为固定脚本比让模型现场生成代码更稳定。脚本可以把重复逻辑和容易出错的细节固化下来，Skill 只负责告诉模型什么时候调用、怎么调用、如何处理结果。这样既能减少上下文消耗，也能提升执行一致性和可调试性。”

一句话总结：

“能固化成脚本的能力，尽量不要每次都让模型临时创造。”

## 39. 执行类脚本应该注意什么

**Q: 如果 Skill 里包含可执行脚本，设计时最该注意什么？**

可以这样回答：

“重点是错误处理、参数文档化和验证机制。脚本应该尽量把常见错误转成明确、可操作的错误信息，而不是把模糊失败留给模型猜。同时所有参数都应该有清晰含义和默认值，避免出现魔法值。对于高风险操作，最好采用 plan-validate-execute 模式，先生成结构化计划，再验证，最后执行。”

## 40. 如果 Skill 依赖外部包或 MCP 工具怎么办

**Q: 当 Skill 依赖外部库、运行环境或 MCP 工具时，应该怎么写？**

可以这样回答：

“依赖一定要显式写清楚，不能默认环境已经具备。包括需要哪些包、在哪个环境可用、是否支持联网安装、是否需要预置资源等。对于 MCP 工具，最好写全限定名，也就是 server name 加 tool name，避免多工具环境下出现歧义。”

工程上可以总结为：

- 不假设环境
- 显式声明依赖
- 工具名尽量完整
- 高风险依赖要验证可用性

## 41. 一个完善的 Skill 上线前应该检查什么

**Q: Skill 在交付前，你会用什么 checklist 做最终检查？**

可以这样回答：

“我会从六个方面检查：一是 frontmatter 是否清晰可路由；二是正文是否紧凑、步骤是否明确；三是目录结构是否支持按需加载；四是术语、路径、依赖是否一致且明确；五是关键流程有没有验证和反馈闭环；六是真实测试用例和目标模型验证是否通过。只有同时满足这些条件，这个 Skill 才算能稳定交付。”

## 42. 更完整的面试总结版

如果面试官希望你系统性总结 Claude Skills best practices，可以直接回答：

“我理解 Claude Skills 的最佳实践，本质上是把高频、高价值、易出错的能力抽象成可按需加载的模块。设计时最重要的是简洁，因为上下文窗口是公共资源；其次要默认模型已经具备通识能力，只补充那些真正缺失的信息。结构上要靠清晰的 frontmatter 做路由，靠紧凑的主文档做流程引导，靠 progressive disclosure 做按需扩展。对于执行类任务，要根据风险选择合适的自由度，高风险任务尽量用脚本、校验和 checklist 固化。最后，Skill 不能只靠写作感觉优化，而要靠真实用例、跨模型测试、用户反馈和持续迭代来验证效果。”
