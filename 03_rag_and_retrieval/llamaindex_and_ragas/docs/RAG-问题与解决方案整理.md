# RAG 问题与解决方案整理（Q/A 版）

## 一、核心痛点与解决方案

### Q1：为什么很多团队做了 RAG Demo，却上不了生产？
A：因为 Demo 阶段只验证“链路可跑通”，生产阶段要面对复杂业务问题、准确性、延迟、成本和合规。RAG 真正难点在全链路工程，而不是单点调用向量库或 LLM。

### Q2：RAG 的第一大坑为什么是文档解析（Parsing）？
A：企业文档不是纯文本，常有双栏排版、表格、图表、页眉页脚。解析一旦错位或乱码，后续检索和生成都建立在错误语料上，结果必然不稳定。

### Q3：解析问题怎么解决？
A：要做“版式还原”，不是只抽文本。具体做法是：
1. 做 Layout Analysis，识别标题层级、正文区、表格区、图注。
2. 表格转为结构化形式（Markdown/HTML/Key-Value）再入库。

### Q3.1：参考 BabelDOC，双栏排版应如何解析？
A：可按 BabelDOC 的思路落地为“先版面、后文本、再顺序重建”：
1. 先做 `PDFParsing` 到中间层（IL），基于 `bbox` 切分文本块，不按行直接拼文本。
2. 在 `ParagraphFinding` 阶段构建段落，结合短行切分（如 `split_short_lines`、`short_line_split_factor`）减少错误断段。
3. 重建阅读顺序时先分列，再列内按从上到下排序；对通栏块（大标题、通栏图注）单独处理，避免跨栏拼接。
4. 表格、公式、图形区域单独解析，不混入正文流。
5. 先用 `--only-parse-generate-pdf` 做可视化验收，再进入翻译/入库/RAG。
6. 入库时保留 `page / bbox / column_id / block_id` 元数据，便于追溯和纠错。

### Q4：固定长度切分（Chunking）为什么容易出问题，且在 B 端更严重？
A：固定切分会截断语义单元，导致前提和结论分离、指代缺失。这是各类 RAG 场景的通用问题；

但在 B 端由于文本结构更复杂、准确性和合规要求更高，代价通常更大。典型后果是模型“看起来会答”，但关键约束丢失，出现错误结论。

### Q5：切分策略怎么优化？
A：采用语义切分 + 父子窗口检索（Parent-Child Retrieval）：
1. 入库时切小块，提升召回精度。
2. 返回时回溯到父块，补足上下文完整性。

### Q6：同一类问题里，为什么“专业术语、缩写、内部编号”特别容易召回失败？
A：因为通用 Embedding 更擅长语义近似，不擅长长尾词项的精确匹配。企业里的型号、缩写、内部代号（如 AX-100-V2-2024）容易被当成噪声，导致该命中的文档没被召回。

### Q7：如果这类场景只做向量检索，会带来什么后果？
A：常见后果是“语义相近但事实错误”。例如用户查 2023 年 Q3 数据，系统可能返回 2022 年内容；答案读起来通顺，但关键事实错了，隐蔽性强、业务风险高。

### Q8：针对 Q6/Q7 这类问题，统一工程解法是什么？
A：采用混合检索（Hybrid Search）：Dense Vector + BM25。Dense 负责语义召回，BM25 负责精确词项（专有名词、编号、缩写、时间词），再通过 RRF 融合排序，兼顾召回率与准确率。

### Q9：为什么要加重排序（Rerank）？
A：向量召回是“海选”，Rerank 才是“精筛”。它能识别 Query 与候选片段的细粒度语义偏差，显著降低“语义对、事实错”。

### Q10：Rerank 的推荐落地方式是什么？
A：两阶段：
1. 向量库快速召回 Top-100（保速度）。
2. Reranker 精排 Top-5 再喂给 LLM（保准确）。

### Q11：什么是“中间丢失（Lost in the Middle）”？
A：这是长上下文推理中的**位置偏置（positional bias）**现象，指模型对“证据放在什么位置”高度敏感。即使证据内容不变，只改变其在上下文中的位置，模型表现也会变化：
1. 关键证据放在开头或结尾时，命中率通常更高。
2. 关键证据放在中间区域时，命中率明显下降（常呈近似 U 型性能曲线）。

这个结论来自“控制变量实验”：研究者保持问题和上下文内容不变，仅移动答案证据所在文档的位置，然后比较问答准确率/检索命中率，结果发现中间位置最容易被忽略。

在 RAG 里，它的直接影响是：即使你召回到了正确片段，如果该片段被塞在长上下文中部，也可能无法被模型有效利用，最终出现“看起来合理但证据没用上”的回答。  
因此它本质是“**证据位置影响任务表现**”的问题，而不只是“上下文太长”本身的问题。
论文来源：Liu et al., *Lost in the Middle: How Language Models Use Long Contexts*, TACL 2024（arXiv: https://arxiv.org/abs/2307.03172）。
原理层面（可能成因，非单一公认机理）：
1. **注意力竞争与稀释**：上下文越长，softmax 注意力在更多 token 上分配，关键证据更容易被“平均化”，有效信号被噪声稀释。
2. **位置与边界锚点效应**：任务提示通常在开头、问题通常在结尾，模型更容易对首尾形成强锚点，中间证据更难获得持续关注。
3. **训练分布偏置**：预训练/指令微调数据中，关键信息常与段首、段尾或问答邻近位置共现，模型会学到“首尾更重要”的经验策略。
4. **长距离位置编码退化**：在超长上下文下，位置编码（如 RoPE）对远距依赖的区分能力会下降，导致中部证据的可分性与可检索性变差。

### Q12：如何缓解“中间丢失”？
A：做动态上下文治理：
1. 删除不相关片段，合并相邻冗余片段。
2. 将最高分证据放在上下文头尾，提升被关注概率。

### Q13：为什么传统“单次检索+生成”处理不好复杂业务问答？
A：很多问题是多跳推理（Multi-hop），需要分步骤取证和组合，单次检索无法覆盖完整推理链。

### Q14：多跳问题的解法是什么？
A：引入 Agentic RAG，把“单次检索+生成”改成“可循环决策”的流程。可按下面 6 步落地：
1. **任务分解（Plan）**：先把复杂问题拆成子问题（如“先查人-部门映射，再查部门销售，再做排序”）。
2. **意图路由（Route）**：为每个子问题选择最合适的数据源和工具（向量库、关键词检索、SQL、搜索 API 等）。
3. **证据执行（Act）**：按子问题逐步检索，保存中间结果和引用来源，不直接一次性生成最终答案。
4. **结果自评估（Reflect）**：判断当前证据是否“足够且一致”（覆盖度、冲突度、时间有效性、是否满足约束条件）。
5. **查询改写与重试（Revise）**：若证据不足或冲突，自动改写查询词并进入下一轮检索（同义词扩展、约束补全、时间词强化）。
6. **终止与回退（Stop/Fallback）**：达到最大步数或置信度仍不足时，返回“无法确定+缺失信息提示”，避免幻觉式硬答。

工程上建议同时加三类控制：`max_steps`（防无限循环）、`budget/token 上限`（防成本失控）、`可追溯输出`（答案绑定证据片段与来源）。

### Q15：GraphRAG 的价值主要体现在哪？
A：适合全局性问题。它通过实体关系图和社区发现，把“碎片检索”升级为“结构化全局理解”，更适合长文档宏观问题。

### Q16：RAG 效果差时，为什么不能先盲目换 Embedding 模型？
A：因为问题可能在解析、切分、召回、重排中的任何一环。未定位根因就换模型，通常只是增加成本。

### Q17：正确的诊断方法是什么？
A：建立可观测体系：
1. 脱离 LLM 先看 Recall（是否召回到正确片段）。
2. 用 RAGas 看 Faithfulness 和 Relevance。
3. 建 Bad Case 标签库，定位到底是解析错、召回错还是重排错。
4. 做向量分布可视化（如 T-SNE）判断语料可分性。

### Q18：RAG 与微调（Fine-tuning）该怎么取舍？
A：RAG 解决动态知识和实时事实，微调解决风格、格式、特定任务逻辑。实践上通常是“通用大模型 + 强 RAG”覆盖大部分场景，再对少数任务做小模型微调。

### Q19：生产落地怎么平衡成本、速度、准确性？
A：可用三件套：
1. 语义缓存：降低重复问题的模型调用成本。
2. 存储分层：热数据内存、冷数据磁盘。
3. 模型路由：简单任务走小模型，复杂推理再走大模型。

### Q20：B 端 RAG 最容易忽视的红线是什么？
A：权限与可追溯性。必须做行级 ACL + 用户身份硬过滤，避免越权检索；输出要能追溯到文档页码/段落，满足审计要求。

## 二、实施顺序（面试常问）

### Q21：如果你来落地，会先做什么？
A：先后顺序建议是：
1. 先做评测与诊断（黄金集 + 指标面板）。
2. 再做召回质量（解析、切分、Hybrid）。
3. 再做答案质量（Rerank + 上下文治理）。
4. 再做复杂能力（Agentic/GraphRAG）。
5. 最后做生产治理（缓存、路由、权限、追溯）。

### Q22：非结构化数据到底要拆多细？
A：核心原则是“语义自洽”。不要切到主谓宾断裂。建议以段落为单位，并保存前后片段关联 ID。

### Q23：Agentic RAG 太耗 Token 怎么办？
A：设置最大循环步数，并提供“否定选项”。如果两轮后仍找不到，就提示用户补充关键词，而不是无限重试。
