ing

![fragm](./paged_attention_assets/15_fragm.svg)

除了缓存体积极其庞大之外，早期的 LLM 服务系统在处理内存分配时也效率低下。这是因为在推理过程中，输出序列的长度事先是未知的。你在自己写提示词时就能想象到这一点：有些提示很短，有些很长，而每个提示既可能生成一段很长且详细的输出，也可能只生成很短的结果。现在把这种情况扩展到成千上万的用户。为了应对这种不确定性，服务平台过去通常会根据每个请求可能达到的最大序列长度，静态地为其分配一块内存，而不管实际输入或最终输出长度是多少。它们通过预分配方案来实现这一点，以确保有足够的内存容纳某个请求*潜在的*最大 KV 缓存大小，即使这部分空间最终根本不会被完全使用。

上图说明了两种碎片化是如何出现的。我改编了论文中的图，但使用了我们在这篇博客中一直沿用的相同示例提示，以保持一致性。这里我把它称为请求 A，旁边还有一个非常简单的请求 B。当然，在实践中你可以想象会有更多请求被一起批处理。正如你所看到的，内存浪费主要有两个来源：

1.  为未来 token 预留的槽位：如果生成提前结束，使用的 token 少于最大值，那么剩余已分配的内存就会一直空着，无法供其他请求使用。这就是**内部碎片**。
2.  来自内存分配器的**外部碎片**，例如伙伴分配器（buddy allocator）。这一点稍微更隐蔽一些，所以我们通过一个例子来说明。

我们从 128 个空闲字节开始。请求 A 到来，需要 32 个字节。分配器不断将这条内存条对半分，直到可以分配出 0 到 31，把 32 到 63 和 64 到 127 留为空闲。请求 B 需要 16 个字节。我们从右侧切出它，把 64 到 127 拆分，再把 64 到 95 拆分，并分配 64 到 79。现在 80 到 95 和 96 到 127 是空闲的，而已分配的块夹在中间。请求 C 很小，只需要 7 个字节。分配器把 32 到 63 一路拆成一个 8 字节的小块，并分配 32 到 39，留下该块内 1 个字节未使用（**内部碎片**）。此时 GPU 仍然总共有相当多的空闲内存：40 到 47、48 到 63、80 到 95 和 96 到 127，加起来共有 72 个字节。但这时又来了一个新的长请求，需要一整块连续的 64 字节。尽管总体空闲内存是足够的，但却没有任何单个连续块有这么大，因为 64 到 79 已经被占用了，而左侧也已经被切分成更小的碎片。于是分配失败。这就是**外部碎片**，而这正是朴素的按请求分配 KV slab 所造成的浪费，因为早期的 LLM 服务系统会把每个请求的 KV 缓存存放在预先分配好的连续内存 slab 中。

这两种碎片化形式本质上都是纯浪费。即使预留内存最终会被消耗掉，在请求的整个生命周期内将其一直保留出来——尤其是当预留空间很大时——也会阻止其他请求在这段时间内使用它。

## 分页作为类比

**Paged Attention** 直接借鉴了类 Unix 和 Windows 等操作系统中的**虚拟内存**与**分页**机制。操作系统不会把内存当作一个巨大的整体块，而是将其划分为页框，并只把活跃的部分保留在高速内存中。

LLM 服务在 KV 缓存上也面临同样的问题。通过对其进行分页，我们可以更高效地分配内存、避免浪费，并支持更长的上下文。在深入讲解分页式 KV 缓存和 paged attention 之前，我认为先快速回顾一下这个操作系统类比会有帮助，这样后面就能更容易建立两者之间的映射关系。

### 操作系统类比

内存压力一直是计算领域中的核心问题。软件的增长速度通常快于内存容量，因此系统需要一种方法来运行那些大于可用内存的程序，同时也要能在多个程序总大小超出可容纳范围时并发运行它们。因此，提出的解决方案就是*虚拟内存*。

这个思路是：每个程序都拥有自己的**虚拟地址空间**，它被划分为固定大小的**页**；而物理内存则被划分为同样大小的**页框**。一个小型映射结构记录着哪个虚拟页当前位于哪个物理页框中。正是由于这种间接映射，程序可以表现得仿佛它的全部内存都存在，尽管实际上系统只会把工作集保留在高速内存中。

例如，设想有一条指令 MOV REG,1000，其中 1000 是某个计算得到的虚拟地址。在没有虚拟内存的系统中，这个地址会被直接送到内存总线，并访问该位置上的字。在有虚拟内存的情况下，一切都要先经过**内存管理单元（MMU）**，它会查阅页表<span class="sidenote-ref"></span> <span class="sidenote"
style="counter-increment:none"> 从数学上讲，页表是一个函数，以虚拟页号为自变量，以物理页框号为输出。 </span>。如果该页存在，访问会立即成功并发送到总线。如果该页不存在（这一点通过硬件中的存在/不存在位表示），MMU 就会触发一次**缺页异常（page fault）**，操作系统随后从较慢的存储中取回缺失的页，将其放入一个空闲页框，更新映射，然后重试该指令。

<img src="./paged_attention_assets/17_transformers.svg"
style="width:80.0%" alt="Transformers" />

</div>

我尝试通过这张图把这个结构说明清楚，不过也许再举个简单例子会更清晰。假设我们有一个 64 KB 的虚拟地址空间，但物理内存只有 32 KB。虚拟空间被划分为 16 个页，每页 4 KB；物理内存被划分为 8 个页框，每个也是 4 KB。如果页表说明虚拟页 0 当前位于页框 2，那么对该页中任意地址的访问都会被重定向到那里。如果虚拟页 2 被映射到页框 6，它就会被送到页框 6。但如果虚拟页 8 被标记为不存在，MMU 就会触发异常，操作系统会从磁盘中取回该页放入某个页框，更新映射，然后程序继续执行。<span class="sidenote-ref"></span><span class="sidenote"
style="counter-increment:none"> 由于地址转换会不断发生，系统需要一些方法来让它足够快。这就是像快表（TLB）和多级页表这类技术发挥作用的地方。这里我们不会深入讲它们，但知道它们的存在是有帮助的。
</span>

关于操作系统这一侧，我们只需要了解这些就够了。虚拟内存通过把一个更大的连续地址空间映射到一个较小的高速内存池上，并根据需要将页换入换出，从而提供了一种大而连续地址空间的*假象*。现在让我们把这些概念带到分页式 KV 缓存，以及后面的 paged attention 中。

### 分页式 KV 缓存

分页式 KV 缓存把同样的分页思想应用到了 KV 缓存上。在 vLLM 内部，**KV cache manager** 是分页式 KV 缓存的核心。它本质上负责管理 keys 和 values 的内存，而**scheduler** 决定每一步哪些请求会继续推进。关键区别在于，cache manager 不会给每个请求分配一个巨大的连续缓冲区来存储它所有的 keys 和 values。相反，它把缓存拆分成固定大小的**KV blocks**，以每块包含的 token 数来衡量——类似于我们之前看到的页——并维护一个**全局空闲块池**，你可以把它看作一个双向链表。同时，它为每个请求分配一个小型的**block table**，用于将其逻辑块映射到 GPU 内存中的物理块（也就是页框）。当请求增长时，就从池中取出新的块并追加到它的表中。当请求结束时，它的块会回收到池里，可立即被其他请求复用。

上半部分是 **engine** 视图，我根据 [Aleksa 的文章](https://www.aleksagordic.com/blog/vllm) 做了改编。请求进入后，processor 会对其进行准备，把原始输入转换成合适的请求格式，也就是分词（tokenisation）；scheduler 决定运行哪些请求；而 KV cache manager 位于中间协调内存。中间部分是我们前面提到的 CPU 侧索引结构，可以把它理解为由 cache manager 管理的、保存可用块标识符的双向链表；底部视图则是真正位于 GPU 上的 KV 数据，以许多大小相同的块形式存储。block table 是两者之间的桥梁，它们同样由 KV cache manager 维护。Block table 是用于将逻辑 KV 块映射到实际计算得到的 KV cache 块的主要表结构，即使这些物理块实际上是分散存放的也没关系。

在初始化时，engine 会测量可用于缓存的 VRAM 数量，选择一个 token 块大小 $`B`$，并计算总共能容纳多少块。对于标准的 transformer 层，每个块的字节数为：

``` math
bytes = 2\times B\times num\_ kv\_ heads\times head\_ size\times bytes
```

其中系数 2 表示同时包含 keys 和 values。在 GQA 或 MQA 中，num_kv_heads 会变得更小，因此每个块更轻，占用更少内存，于是相同内存中可以容纳更多块。

在执行过程中，vLLM 采用的是即时分配，而不是预测完整的未来长度。在每个 engine step 中，scheduler 决定哪些请求要推进，然后要求 KV cache manager 仅为本步处理的 token 预留块。对于 prefill，新 token 的数量是事先已知的，因此 manager 会为一个包含 $`N`$ 个 token 的提示分配 $`\lceil N\div B\rceil`$ 个块。对于 decode，这一步通常只会新增一个 token<span class="sidenote-ref"></span>
<span class="sidenote" style="counter-increment:none">  
在 V1 中，engine scheduler 可以在同一步中混合 prefill 和 decoding 阶段。而在 V0 中——为了简化并与 Aleksa 的文章保持一致，这里我采用的是这种描述——任意时刻只能发生其中之一。  
</span>。manager 会检查最后一个逻辑块中剩余的空槽，并且只有当该块会在本步溢出时才分配一个新块。类似地，当一个请求完成后，它的块会被归还到池中。由于每个块的大小都相同，任何一个归还的块都可以满足未来任意块请求。

这两张图展示了一个简单提示在逻辑视图和物理内存视图中的样子，以及它们如何映射到 block table 中。假设该提示有 7 个 token，且 $`B = 4`$。我们需要 $`\lceil 7\div 4\rceil = 2`$ 个 KV 块。manager 从空闲池中弹出两个标识符，并把它们写入该请求的 block table。每个条目会跟踪物理块 id、一个小型引用计数，以及通常还有一个块哈希值。引用计数支持内存共享。当两个请求共享相同的前缀时，它们都会指向相同的物理块，而计数会增加。无需进行任何拷贝，我们下一节会看到这一点。在 decode 期间，新 token 会被写入下一个空闲槽位。当最后一个块被填满时，就会再追加一个块，而表也会增长一个条目。

这里有一个至关重要的说明需要明确：块是共享读取、独占写入的。一个物理 KV 块的写权限只属于单个请求。你绝不会允许一个无关请求把 token 写进别人块中的剩余空槽里。如果两个请求共享相同的前缀，它们可以共同读取这些块，而引用计数会增加。一旦其中某个请求需要追加内容，cache manager 就会为该请求分配一个新的块，这实际上就是以块粒度进行的写时复制（copy on write）。正如你会意识到的，这意味着在一个请求最后一个块中，可能会留下一些小的未使用尾部，而这正是
