# Harness Engineering 蒸馏笔记

这篇文档记录的是一条方法论线索：如何把 OpenAI 关于 Harness Engineering 的文章，蒸馏成适用于本地 Agent 工作流的工程实践。

它不是 Skill 使用手册，也不是某个具体仓库的部署说明。重点在于：

- 文章里哪些机制可以直接借用
- 哪些思路可以借鉴，但实现必须按本地环境重写
- 哪些做法在当前场景下不值得照搬

## 来源

- OpenAI 官方文章：
  - *Harness engineering: leveraging Codex in an agent-first world*
  - 发布日期：2026 年 2 月 11 日
  - 作者：Ryan Lopopolo
  - 链接：https://openai.com/index/harness-engineering/

原文讨论的是 OpenAI 团队如何围绕 Codex 设计一套能让 Agent 持续工作的执行环境。核心结论不是“模型更强了”，而是当 Agent 成为主要执行者之后，工程重点会从“人直接写代码”转移到“人设计环境、约束、反馈回路和恢复机制”。

## 为什么这篇文章值得单独放一个专题

第一次读完这篇文章，最有价值的部分不是某个单点技巧，而是它把几个长期痛点讲透了：

- Context 重置后，Agent 不知道上一轮干了什么
- 任务跑到一半，Agent 很容易因为“看起来差不多了”而提前停下
- 遇到模糊边界时，Agent 会卡在原地等人工确认

这些问题本身并不依赖 OpenAI 的云端基础设施，本地 Agent 工作流同样会遇到。区别只在于实现方式不同。

因此，这篇文章适合作为一个独立的扩展专题，而不是塞回某个已有主线目录里。它更像一套“Agent-first 工程化方法论”，和具体框架、具体业务都有关，但又不完全等同于其中任何一个主题。

## 读这篇文章时在想什么

原文给出的几个数字非常有冲击力：三名工程师、五个月、约一百万行代码、零手写代码、平均每人每天约 3.5 个 PR。它呈现出的不是“单个 Agent 很神”，而是一种新的工程组织方式：

- Humans steer, agents execute
- 人的主要工作不再是写代码，而是设计环境、表达意图、建立反馈循环
- 当 Agent 无法稳定完成任务时，优先问“环境缺了什么”，而不是“能不能再试一次”

这和传统的 Prompt 优化视角不太一样。真正拉开差距的不是一句 Prompt 写得更像人，而是仓库结构、知识组织、结构约束、验证机制、恢复机制是否足够机械化。

## 蒸馏的方法

读这类文章时，一个有效的方法是把内容分成三类：

### 1. 直接可用的机制

这些机制的目标和实现逻辑足够清晰，可以直接借用：

- 进度文件就是上下文
  - 原文把 execution plans、progress logs、decision logs 版本化存进仓库，用来解决 Context 重置后的恢复问题
  - 这类思路完全适合本地环境
- `AGENTS.md` 作为目录，不作为百科全书
  - 大而全的单一说明文件会快速腐烂，还会抢占有效 Context
  - 更合理的做法是让 `AGENTS.md` 只承担导航功能，真正的知识沉到结构化文档目录
- 用结构测试机械执行架构规则
  - 当约束由 linter 和结构测试执行时，Agent 不需要“记住规范”，只需要响应错误并修复
  - 如果错误信息里顺带包含修复指引，效果会更好

### 2. 思路可借鉴，但实现要改

这些思路成立，但不能原样照搬：

- 可观测性直接交给 Agent
  - OpenAI 的做法是给每个 worktree 配一套独立日志、指标、Trace 查询能力
  - 如果你的重点是性能和系统行为分析，这非常合理
  - 但在以业务流验证为主的本地环境里，更实用的替代品可能是“证据包”：`verdict.json`、请求响应记录、数据库快照、过滤后的日志
- Entropy 管理
  - 原文提到 agent 会复制仓库中的现有模式，好的坏的都会复制，时间长了就会 drift
  - 这个判断完全正确
  - 但后台自动扫描修复并不是唯一解，本地环境也可以先从 golden principles + 结构测试 + allowlist ratchet 开始

### 3. 对方能做，但当前不考虑

有些做法在对方场景里合理，但不一定适合自己的环境：

- 放松合并门禁
  - 原文提到部分场景下不会让 flaky tests 无限阻塞进度
  - 对内部工具可能可接受，但涉及支付、订单、履约等业务时，blocking checks 仍然是底线
- 全量 agent-to-agent review 替代人工
  - 这个方向可行，但实现方式可以不同
  - 比如用一个 Agent 负责开发，用另一个 Agent 做 review，也是一种很自然的落地方式

## 四个 Skill 是怎么被蒸馏出来的

把问题拆开看之后，最终会自然落到四层：

### 1. `harness`

关注点：让 Agent 能持续跑，跑断了还能恢复。

对应问题：

- 任务执行时间过长
- session 中断后状态丢失
- Agent 需要快速理解“上次做到哪了”

典型机制：

- 任务清单文件
- 进度日志文件
- 决策日志
- 与 `git log` 联合恢复上下文

### 2. `closed-loop-testing`

关注点：验证结果来自业务不变式，而不是“脚本退出码为 0”。

对应问题：

- 业务流测试只是跑完了，但并不知道结果是否正确
- 外部服务不稳定导致整条链路反复重跑
- 缺少可复核的证据

典型机制：

- 分阶段验证
- replay 模式
- `verdict.json`
- 请求响应记录
- 数据库快照
- 过滤后的日志证据

### 3. `architecture-guardrails`

关注点：把架构约束写成机器可执行规则，而不是靠 Agent 自觉。

对应问题：

- Agent 会复制仓库里已经存在的坏模式
- 人类口头约束无法持续生效
- 架构边界一旦模糊，速度越快腐化越快

典型机制：

- 分层约束
- 自定义 linter
- 结构测试
- 带修复指引的错误信息
- allowlist + ratchet

### 4. `harness-marathon`

关注点：让任务不是“跑一下”，而是“持续跑到真正完成”。

这个部分不是原文里的原封不动复述，而是对长期运行规律的再抽象。

可以把 Agent 停下来的原因归成三类：

- 工作真的做完了
- 遇到不确定点卡住了
- Context 退化了，无法继续稳定推进

把这三类原因逐个消掉，Agent 的单次连续运行时间才会上去。

## 跑了几周之后，哪些感受最真实

几个经验尤其值得写进文档：

### 进度文件非常值钱

长任务里，session 断开是常态，不是例外。只要任务超过几个小时，就应该默认它随时可能中断。没有进度文件时，Agent 会花大量时间重新理解状态，而且很容易理解错。

### “Zero decision points” 很容易被低估

很多停顿都不是模型能力问题，而是 Prompt 漏掉了外部依赖、测试数据位置、密钥来源、已知异常分支的处理方式。任务跑到中途再回来补这些信息，成本非常高。

### Doom Loop 需要机械检测

如果同一个文件被反复编辑，通常意味着当前思路已经卡死。把“同文件编辑次数过多”做成报警条件，比事后人工复盘更有效。

### 分阶段验证比一把梭稳得多

先验证内部可控路径，再逐步接入外部回调和完整证据包，会显著提升通过率，也更适合长任务持续推进。

### 异构 Agent 互审比单 Agent 自审更稳

开发和 review 交给不同 Agent，往往比“写完再自己 review”更容易发现盲点。这和原文里的 agent-to-agent review 是同一方向，但本地实现完全可以更灵活。

## 这篇文章真正教会人的，不是某个技巧

真正值得带走的是三连问：

### 1. 这个做法在解决什么问题

不要停在“他们做了什么”。要继续追问：这个机制背后到底在解决哪个失败模式。

例如，把 execution plans 存进仓库，表面上看是文档习惯，实质上是在解决“Context 重置后的状态恢复”。

### 2. 这个问题在我的场景里是否存在

如果问题在自己的场景里根本不存在，就没有必要为了“看起来先进”而照搬整套机制。

### 3. 有没有更简单的实现，也能解决同一个问题

很多时候，最有效的蒸馏不是复制全部基础设施，而是保留问题定义，替换实现手段。

OpenAI 的方案是面向 Codex 云端和自研基础设施的；本地环境更应该关心最小可行机制，而不是追求外形一致。

## 适合怎么读这篇文档

这篇文档更适合以下几类读法：

- 正在设计本地 Agent 执行环境时，把它当作问题清单
- 正在写 Skill 或流程约束时，把它当作机制来源
- 正在复盘长任务为什么中途停掉时，把它当作故障分类框架

如果你只是想知道“这个 Skill 怎么用”，这篇文档不是入口。它更适合作为上游方法论，帮助你判断为什么需要这些机制，以及它们各自解决什么问题。

## 一句话总结

从这篇文章里最值得蒸馏出来的，不是某套专有基础设施，而是一个判断标准：

当 Agent 跑不动时，先不要怀疑 Prompt，先看环境、约束、验证和恢复机制是不是还不够工程化。
