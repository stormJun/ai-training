## 一、背景与适用范围

这批文档总结的不是通用大模型训练理论，而是一个比较具体的 NLU 微调场景经验：

- 任务类型：意图识别 + 槽位抽取
- 典型模型：`Qwen/Qwen2.5-7B-Instruct`
- 训练方式：SFT / LoRA / QLoRA
- 问题表现：联合准确率低、槽位幻觉、槽位边界不一致、意图混淆、评估结果不稳定

这些经验对“结构化抽取类微调”尤其有用，对纯对话生成类任务可以部分借鉴，但不能直接照搬。

## 二、最重要的结论

### 1. 微调更像“调优”，不是“重塑”

如果数据口径、评估格式、槽位 schema 本身不稳定，微调不会替你自动学出一致规则。模型只会把混乱放大，然后在评估里表现为：

- 同一语义多种槽位写法
- 查询类语句补出不存在的默认值
- 同一个词被抽成不同 type
- 同义但字符串不完全相同，导致评估算错

换句话说，先解决“规则不一致”，再谈“模型没学会”。

### 2. 数据问题通常比参数问题更大

任务23和任务27两轮分析里，最核心的问题都不是“学习率选错了”，而是：

- 标注口径不一致
- 意图边界不清
- 槽位类型定义不收敛
- 值归一化规则缺失
- 查询类空槽位负样本不足

参数优化有价值，但优先级在数据规范之后。

### 3. 训练格式和评估格式必须完全一致

这是一条非常关键的工程经验。

分析任务23时，发现训练使用的是 Qwen role token 格式，而评估和部分 Prompt 测试入口使用的是纯文本格式。结果是模型在评估时看到的输入分布和训练时不同，直接导致：

- 查询类语句幻觉严重
- 指标不能真实反映模型能力
- 同一个模型在不同入口表现不一致

这类问题会伪装成“模型能力不足”，但本质上是评估链路有缺陷。

### 4. 槽位错误往往是主矛盾

任务23里，错误主体是 `slot`；任务27虽然整体指标明显更高，但剩余错误依旧主要集中在：

- `time` / `timeofday`
- `event_name`
- `date`
- `person`
- `relation`
- `general_frequency`

这说明在结构化抽取任务里，后期瓶颈通常不是意图识别，而是槽位定义、边界和归一化。

### 5. 错误分析系统本身要可信

如果错误样本表、错误判定逻辑、前端展示方式本身有缺陷，那么后续优化方向也会被带偏。

这批文档里一个很重要的经验是：评估系统不是附属品，它本身就是微调闭环的一部分。

## 三、核心根因归纳

### 1. 数据与标注口径问题

最典型的问题包括：

- 同一时间表达被拆成 `time + timeofday`，或直接合并成一个 `time`
- `event_name` 是否应包含人名、修饰词、动作短语，标准不一致
- `person` / `relation` 值是否保留尾部“的”，不一致
- `general_frequency` 是整体保留，还是拆成 `date + frequency`，不一致
- `date`、`event_name`、`time_zone`、`place_name` 等 type 之间边界重叠

这类问题的特点是：模型预测可能“语义没错”，但因为 schema 没收敛，最终仍然评估失败。

### 2. 查询类语句的默认值幻觉

任务23里很典型的一类错误是：

- 用户没有给出明确时间
- 标准答案应该是空槽位
- 模型却补出 `今天/明天/早上7点/晚上10点`

这通常意味着：

- 训练集中空槽位查询样本不够
- system prompt 没把“不得凭空补值”说清楚
- 训练/评估 prompt 格式不一致

### 3. 意图边界模糊

任务23、任务27里都出现了高频混淆：

- `calendar_set` ↔ `calendar_query`
- `calendar_query` ↔ `recommendation_events`
- `alarm_set` ↔ `alarm_query`
- `general_quirky` ↔ 更具体意图

根因不是单纯样本少，而是标签边界本身模糊，导致模型面对模棱两可表达时没有稳定标准。

### 4. 评估链路和错误判定问题

从 `EVALUATION_ERROR_ANALYSIS.md` 可以提炼出几条很重要的工程经验：

- 错误明细表只保存一个子集，不能直接等价于全量错误分布
- 当前错误入库有上限，适合排障，不适合做全量统计
- 槽位比较逻辑如果先 `set` 去重，会把“重复槽位”误判为正确
- 前端如果展示的是去重后的结果，会隐藏一部分真实问题

所以“错误分析系统可视化出来的结论”本身也要被审计。

### 5. 训练与推理工程细节问题

文档里提到的高频工程问题包括：

- `num_epochs` 太低，可能欠拟合
- `lora_r` 与注入模块容量不足
- `max_seq_length` 需要先验证是否真的截断，再决定是否调大
- loss 只应在 assistant 输出区间计算
- 评估阶段解码参数要稳定，避免把格式漂移误认为模型能力问题

这些问题重要，但通常排在数据和格式一致性之后。

### 6. 运维与环境稳定性问题

任务27里还暴露了两类非模型问题：

- 评估依赖远端模型下载，网络不稳定会失败
- 后端重启会直接中断正在运行的评估线程

这提醒我们：评估稳定性不只取决于模型，也取决于运行链路。

## 四、任务23与任务27的经验对比

### 任务23的意义

任务23更像“问题暴露期”。

它揭示了：

- 查询类幻觉严重
- 槽位错误占绝对主导
- 训练/评估 prompt 不一致
- 标注口径本身有较多冲突

所以任务23最大的价值不是指标本身，而是帮助定位了“根因到底在数据、格式还是模型”。

### 任务27的意义

任务27更像“修了一轮之后的稳定性检查”。

它显示：

- 意图准确率和槽位 F1 已明显提升
- 解析错误基本稳定
- 剩余问题开始从“严重幻觉”转向“schema 不一致”和“边界不清”

这说明优化进入了第二阶段：不是先救火，而是开始做规范收敛。

### 两轮经验合起来说明什么

如果任务23代表“底层问题暴露”，任务27代表“规范不收敛的残留问题”，那么合起来得到一个比较清晰的演进路径：

1. 先修评估链路和 prompt 一致性
2. 再修数据 schema 和标注口径
3. 然后才做参数优化
4. 最后才考虑后处理和补丁式修复

## 五、可复用的方法论

### 1. 微调前：先做数据治理

在开始训练前，至少要先回答清楚这些问题：

- 每个 intent 的边界是否互斥
- 每个 slot 的 type 是否唯一且稳定
- 同一语义是否只允许一种主写法
- 是否需要值归一化规则
- 查询类样本里空槽位比例是否足够

如果这些问题没定下来，训练越久，错误模式越复杂。

### 2. 微调中：保持训练、评估、测试同构

训练、评估、Prompt 测试三条链路的输入格式必须尽量完全一致，尤其是：

- system prompt
- role token 结构
- output JSON 约束
- 解码参数

否则你看到的是“不同输入模板下的表现差异”，不是模型本身能力差异。

### 3. 微调后：先用错误分析驱动下一轮数据修复

不要一看到错误就先改学习率。更高性价比的顺序应该是：

1. 看错误类型分布
2. 看高频意图混淆对
3. 看高频槽位冲突
4. 看值归一化是否缺失
5. 补边界样本和负样本
6. 再做参数实验

### 4. 后处理只能做最后兜底

文档里多次强调：后处理不是主方案。

如果本体问题是 schema 不一致、标注冲突、训练和评估链路不一致，那么后处理只能暂时遮住问题，不能真正提高模型可迁移性和可复用性。

## 六、建议的落地顺序

如果后续再做类似项目，推荐按这个顺序推进：

1. 统一训练、评估、测试 prompt 格式
2. 固化 canonical system prompt 和 JSON 输出约束
3. 统一 intent 边界定义
4. 统一 slot schema、边界和取值规范
5. 增加查询类空槽位负样本
6. 增加易混淆 intent 的对照样本
7. 建立 SQL + 错误样本表的分析流程
8. 验证评估逻辑是否掩盖重复槽位、多槽、值边界问题
9. 重新评估，确认错误类型是否转移
10. 最后再做 LoRA / epoch / seq length 等参数搜索

## 七、可以直接复用的经验规则

### 规则1

结构化抽取任务里，优先优化数据定义，不要先优化超参数。

### 规则2

评估链路必须和训练链路同构，否则指标没有参考价值。

### 规则3

如果 `slot` 错误远高于 `intent` 错误，优先检查：

- schema 是否稳定
- 值归一化是否存在
- 查询类空槽位样本是否充足

### 规则4

如果模型“经常幻觉补值”，优先怀疑：

- prompt 格式不一致
- 负样本不足
- system prompt 约束不够

### 规则5

如果多轮训练后剩余错误主要是“同义不同写法”，说明问题中心已经从模型能力转移到了评估口径和标注规范。

## 八、一句话总结

这批文档最终沉淀出的核心经验是：

**微调效果的上限，往往先由数据规范、评估一致性和错误分析系统决定，然后才由模型参数决定。**

如果前者不稳，后者再怎么调，也只是在不稳定地放大已有问题。
