## 一、这份项目可以怎么对外介绍

### 30 秒版本

我做的是一个面向 NLU 结构化抽取场景的微调项目，任务是意图识别加槽位抽取，底座模型主要是 `Qwen2.5-7B-Instruct`，训练方式用过 SFT、LoRA 和 QLoRA。项目里我重点做了三件事：第一，定位微调效果差到底是数据问题、评估问题还是模型问题；第二，建立错误样本分析闭环；第三，把训练、评估、Prompt 测试链路统一起来，避免指标失真。

### 90 秒版本

这个项目本质上是一个 NLU 微调和评估闭环。任务形式不是纯对话生成，而是比较典型的结构化抽取，也就是给用户一句话，模型输出意图和槽位 JSON。我们一开始遇到的问题是，联合准确率不高，而且查询类语句有明显幻觉，比如输入没有时间，模型会补出“今天”“明天”“早上7点”之类的默认值。

后面我把问题拆成三层去看。第一层是工程链路，发现训练和评估用的 prompt 格式并不一致，这会直接让评估失真；第二层是数据和 schema，发现很多错误不是模型没学会，而是标注口径本身不一致，比如 `time` 和 `timeofday` 怎么拆、`event_name` 要不要带人名、`person` 要不要保留“的”；第三层才是训练参数和 LoRA 容量。

最后得到的经验是，在这种结构化抽取任务里，效果上限往往先由数据规范、评估一致性和错误分析系统决定，然后才由超参数决定。

## 二、最适合面试先讲的结论

### 结论 1：先别急着调参，先看数据和评估链路

**短回答版**

我这个项目里最关键的经验是，结构化抽取类微调任务中，数据定义和评估链路通常比超参数更决定上限。如果 schema 没收敛，或者训练和评估 prompt 不一致，模型表现差不一定是“没学会”，而可能是“学了一个不稳定目标”。

**深入展开版**

这是因为结构化抽取不是开放式生成，而是“在固定 schema 下输出稳定 JSON”。这种任务的误差来源主要有三类：

1. **目标本身不稳定**
   - 同一语义在训练集中有多种标法
   - 同一个值在不同样本里属于不同 type
   - 同一 intent 的边界不清

2. **输入分布不一致**
   - 训练用的是 Qwen role token 格式
   - 评估却用纯文本格式
   - 模型在推理时看到的并不是训练时熟悉的模板

3. **模型容量或参数问题**
   - epoch 太低
   - LoRA rank 太小
   - target modules 容量不足

在项目里，前两类问题的收益通常比第三类更高，也更稳定。

### 结论 2：训练、评估、测试三条链路必须同构

**短回答版**

我在项目里遇到过一个非常典型的问题：训练和评估的 prompt 格式不一致，结果导致查询类语句出现严重幻觉。这个经验让我意识到，很多时候我们以为在优化模型，其实是在修评估链路。

**深入展开版**

原理上，这属于 **distribution shift**。模型训练时学到的是一种输入模板分布，如果评估时给它另一种模板，哪怕语义看起来一样，模型内部激活也会发生变化。对结构化抽取来说，这种变化会体现在：

- 更容易补值
- 更容易格式漂移
- 更容易把“空槽位”理解成“需要补全的槽位”

项目里的具体表现是：

- 训练使用 Qwen role token 格式
- 评估和部分 Prompt 测试入口使用的是“输入：... 输出：...”纯文本模板
- 结果任务23里查询类幻觉非常明显

修复后，不只是指标更合理，问题定位也更清晰，因为训练、评估、测试终于在看同一件事。

### 结论 3：槽位问题往往比意图问题更难

**短回答版**

项目里最主要的错误不是 intent，而是 slot。意图通常是一个分类问题，而槽位本质上是“边界 + 类型 + 值规范”三件事叠加，所以后期瓶颈大多会落在槽位抽取上。

**深入展开版**

可以把 intent 和 slot 的难度理解成两种不同类型的学习：

- **intent**：更像句子级分类，关注整体语义
- **slot**：更像结构化抽取，既要知道抽什么，又要知道抽多长、用什么 type、值要不要归一化

在任务23和任务27里，剩余高频错误主要集中在：

- `time` / `timeofday`
- `event_name`
- `date`
- `person`
- `relation`
- `general_frequency`

这说明模型后期不是“不懂句子”，而是“懂了大意，但 schema 没有对齐”。

## 三、面试官高频问题与回答模板

## 1. 你是怎么判断问题在数据、评估还是模型本身的？

**短回答版**

我不是直接从训练 loss 或最终 accuracy 反推，而是先拆链路。先看训练、评估、测试三条链路是否一致，再看错误样本分布，最后才看训练参数。这个顺序可以避免把工程问题误判成模型问题。

**深入展开版**

我的诊断顺序大概是：

1. **先看输入输出链路**
   - 训练 prompt 和评估 prompt 是否一致
   - 测试入口是否和评估模板一致
   - loss masking 是否只覆盖 assistant 输出区间

2. **再看错误分布**
   - `intent` 多还是 `slot` 多
   - 高混淆 intent 对有哪些
   - 高发 slot 类型有哪些

3. **再看 schema 和数据口径**
   - 同义值是否多种写法
   - 同一字段是否被拆分/合并不一致
   - 是否缺少空槽位查询样本

4. **最后再看参数**
   - epoch 是否过低
   - LoRA 容量是否不足
   - max sequence length 是否真的截断

这种顺序的好处是，先排除“系统性错误”，再做“模型能力优化”。

## 2. 你为什么说数据问题比调参更优先？

**短回答版**

因为调参优化的是“在当前目标下学得更好”，但如果当前目标本身不稳定，比如标注口径冲突、schema 不一致，那你只是让模型更稳定地学到冲突。

**深入展开版**

举几个项目里的典型例子：

- `time="下午四点"` 和 `time="四点" + timeofday="下午"` 混着出现
- `event_name` 有时包含人名，有时把人名单独拆成 `person`
- `person` 和 `relation` 是否保留尾部“的”不一致
- `general_frequency` 有时保持整体，有时拆成多个字段

这些问题一旦存在，模型会面临一个本质上不确定的监督信号。此时调大 rank、加 epochs，只会更好地拟合这种不稳定目标。

## 3. 你们是怎么做错误分析闭环的？

**短回答版**

我们把评估汇总指标和错误样本明细拆开存。汇总指标看趋势，错误样本看具体模式，然后用 SQL 和前端错误表格去定位高频问题，再反向驱动数据修复和 prompt 修复。

**深入展开版**

项目里有两类核心表：

- `fine_tune_evaluations`
  - 看整体指标，比如 `intent_accuracy`、`slot_f1`、`joint_accuracy`
- `fine_tune_evaluation_errors`
  - 看具体错误样本，包括输入、预测意图、标准意图、预测槽位、标准槽位、错误类型

使用方式上：

1. 先通过汇总指标判断模型大盘是否变好
2. 再从错误明细中看：
   - 高混淆 intent 对
   - 哪些 slot 类型最容易 FP/FN
   - 是否存在查询类补默认值
3. 然后把这些发现转成数据修复动作：
   - 补边界样本
   - 补负样本
   - 收敛 schema
   - 增加值归一化规则

这个闭环的关键不是“看错误”，而是让错误分析能稳定地驱动下一轮数据改造。

## 4. 你们为什么会出现查询类幻觉？是模型能力不够吗？

**短回答版**

不完全是模型能力问题。项目里查询类幻觉更多是由三件事叠加造成的：prompt 格式不一致、空槽位负样本不足、system prompt 对“不得补值”的约束不够明确。

**深入展开版**

以“我有设任何闹钟吗”这种句子为例，标准答案应该是空槽位。但模型会补出：

- `今天`
- `明天`
- `早上7点`
- `晚上10点`

这类现象的成因通常是：

1. **模板误导**
   - 模型在评估时没看到训练时的 token 结构

2. **负样本不足**
   - 训练集中大量样本是“有明确值的抽取”
   - 模型被强化成“只要看到 query，就尽量抽点东西”

3. **结构化约束不够**
   - 没把“值必须可从输入追溯”写清楚

所以解决方案也应该是链路一致化 + 负样本补充 + 提示约束，而不是直接把温度调低了事。

## 5. 你是怎么理解 LoRA / QLoRA 在这个项目里的作用的？

**短回答版**

在这个项目里，LoRA / QLoRA 主要解决的是“在有限资源下让模型适配特定抽取 schema”，但它们优化的是容量和成本，不解决数据口径本身冲突的问题。

**深入展开版**

面试里可以这么展开：

- **LoRA 的价值**
  - 在不全量更新的情况下，让模型快速适配领域任务
  - 适合结构化抽取这种指令偏置较强的任务

- **QLoRA 的价值**
  - 进一步降低显存开销
  - 适合在单机或资源受限环境下做 7B 级别实验

- **项目里的实际认知**
  - `lora_r` 决定的是适配器容量，不是万能旋钮
  - 还要结合 `target_modules`
  - 如果 schema 自身冲突没解决，LoRA 容量再大，也只是学到更稳定的冲突

如果面试官继续追问，可以再补：

- rank 太小可能欠拟合复杂槽位边界
- rank 太大可能提高训练成本但不一定带来有效收益
- 是否值得调大，取决于数据已经足够干净没有

## 6. 你会怎么回答“为什么 slot 比 intent 更难”？

**短回答版**

因为 slot 不是单一分类问题，而是“抽取边界 + 字段类型 + 值规范化”三件事叠加，所以比 intent 更容易受标注口径和评估策略影响。

**深入展开版**

可以从三个层次讲：

1. **边界层**
   - 值应该抽到哪里为止
   - 修饰词要不要带上
   - “的”要不要保留

2. **类型层**
   - 同一个词到底是 `event_name`、`person`、`relation`、`date` 还是 `place_name`

3. **归一化层**
   - 等价表达是否需要统一
   - 中英混合值是否允许
   - 复合字段是拆开还是保留整体

intent 只需要判断“这句话主要在干嘛”，slot 则需要判断“这句话里每个值怎么被结构化”。复杂度天然更高。

## 7. 如果让你继续优化这个项目，你会怎么做？

**短回答版**

我不会先做大规模调参，而会先把 schema、评估一致性和错误分析系统修到稳定，然后再做针对性的 LoRA 容量和训练轮数实验。

**深入展开版**

我的优先级会是：

1. 统一训练、评估、测试模板
2. 固化 canonical system prompt 和 JSON 输出约束
3. 收敛 intent 边界
4. 收敛 slot schema 和取值规则
5. 增加查询类空槽位负样本
6. 增加边界混淆样本
7. 修复错误分析系统对重复槽位、多槽的判定缺陷
8. 再做 LoRA rank、target modules、epoch 的组合实验

这个顺序的原因是，越靠前的步骤越能提高“优化的可信度”。

## 四、面试官继续追问时可以怎么讲原理

## 1. 为什么训练与评估 prompt 不一致会影响指标？

可以从两个角度回答：

- **经验角度**
  - 模型在训练时习惯了某种模板，评估时换模板会导致行为漂移

- **原理角度**
  - 大模型不是只学语义，也学 token pattern
  - 特定 role token、结构分隔符、前缀形式会影响注意力分布和输出先验
  - 对结构化 JSON 任务来说，这种先验尤为敏感

## 2. 为什么负样本重要？

因为结构化抽取模型很容易形成一个错误先验：

- “用户一说 query，我就应该抽到点什么”

如果训练集中大部分 query 样本都带明显槽位，模型就缺少“该输出空集合”的监督信号。负样本的作用，是让模型学会“不是每次都要抽值”。

## 3. 为什么说错误分析系统本身也要评估？

因为你依赖它来做优化决策。

如果错误分析系统：

- 对重复槽位去重
- 对多槽和缺槽不区分
- 只存错误样本前 500 条
- 前端隐藏原始输出细节

那么你看到的“错误模式”就可能被系统自身扭曲。此时你优化的未必是模型真正的问题。

## 4. 为什么 loss masking 是个面试加分点？

因为它能说明你理解“训练信号到底落在哪”。

对于 instruction / messages 格式的 SFT：

- 如果 system 和 user 区域也参与 loss
  - 模型会被鼓励去复述 prompt 模板
  - 训练目标会被污染

- 如果只对 assistant 区间算 loss
  - 训练目标更纯净
  - 更符合“根据输入生成结构化输出”的任务定义

这个点往往比“学习率调了多少”更能体现你是否真的理解训练过程。

## 五、项目复盘故事线，适合在面试里完整讲

如果面试官让你讲一个完整案例，可以按下面的顺序说：

1. **项目目标**
   - 做一个 NLU 微调和评估闭环，输出意图和槽位 JSON

2. **初始问题**
   - 联合准确率不高，查询类幻觉明显

3. **第一轮排查**
   - 不是先调参数，而是先检查训练、评估、测试链路
   - 发现 prompt 格式不一致

4. **第二轮排查**
   - 通过错误样本表和案例分析，发现大量问题来自 schema 和标注口径

5. **核心结论**
   - 在结构化抽取微调任务里，数据规范和评估一致性优先于调参

6. **后续优化方向**
   - 统一模板
   - 收敛 schema
   - 构造负样本和边界样本
   - 再做 LoRA 容量实验

这样讲的优点是，能同时体现：

- 你会看系统
- 你会做诊断
- 你不是只会盲目调参
- 你能把模型问题和工程问题分开

## 六、面试里容易加分的表达

下面这些说法比较容易让面试官觉得你不是只停留在表面：

- “我会先判断这是 supervision problem、evaluation problem，还是 optimization problem。”
- “结构化抽取任务里，slot error 很多时候是 schema 不收敛，而不一定是模型理解力不够。”
- “如果训练和评估模板不一致，指标本身就不再是纯净的模型能力指标。”
- “错误样本系统本身也可能有偏差，所以我会审计 error logging 和 slot comparison 逻辑。”
- “LoRA 解决的是资源约束下的适配问题，不替代数据规范化。”

## 七、面试里最好避免的表达

- “这个问题就是因为模型太小。”
  - 太武断，没有先排除数据和评估问题。

- “我把 learning rate 调了几轮，效果就好了。”
  - 说明诊断顺序可能不够成熟。

- “slot 错误多就是模型抽取能力不行。”
  - 忽略了 schema、标注和评估定义。

- “我们指标低，所以继续堆数据就行。”
  - 如果数据口径没统一，堆数据可能会扩大噪声。

## 八、最后的一句话版本

如果面试官最后只想听一句总结，可以这样说：

**这个项目让我真正建立起来的认知是，LLM 微调不是简单调参，而是一个从数据定义、训练目标、评估链路到错误分析系统都必须闭环一致的工程问题。**
