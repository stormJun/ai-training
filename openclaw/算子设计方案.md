# 算子设计方案

> 基于《用 OpenClaw 突破企业传统数据资产架构的实践》整理和扩展。
> 本文档关注“算子化数据资产平台”的工程设计，重点说明如何用 Python 抽象数据接入、清洗、标注、质量评估、血缘和发布等能力。

## 1. 背景

传统企业数据资产平台通常把数据接入、治理、清洗、标注、质量检查、发布等能力封装在一个平台内部。这样做的问题是：

- 功能之间耦合重，某个流程要改动时容易影响整个平台。
- 能力复用困难，不同业务线经常重复实现类似的数据处理逻辑。
- API 管理困难，历史接口多，但缺少统一的输入输出规范。
- 编排能力弱，难以让智能体、调度系统或工作流引擎自动组合使用。
- 审计和血缘不完整，无法清晰回答数据从哪里来、经过了什么处理、由谁发布。

算子化的目标是把平台里的核心能力拆成一组标准化、可注册、可执行、可编排、可治理的处理单元。每个算子都是一个明确的业务能力，例如数据接入算子、清洗算子、标注算子、质量评估算子、血缘算子、发布算子。

## 2. 设计目标

本方案采用四个核心原则：

1. **Schema 化**
   所有算子的输入、输出、参数、运行上下文都必须结构化，优先使用 Pydantic 定义数据契约。

2. **Registry 化**
   所有算子都必须可以注册、发现、查询和版本管理，避免能力散落在代码、脚本或临时 API 中。

3. **Executor 化**
   所有算子必须通过统一执行入口运行，由执行器统一完成输入校验、权限检查、日志、状态、异常、指标和血缘记录。

4. **DAG 化**
   算子之间不互相硬编码调用，而是由工作流层编排。算子只关心自己的输入、输出和业务逻辑。

## 3. 核心概念

### 3.1 算子是什么

算子是平台中的最小可执行能力单元。它不是普通函数，也不是单纯的 HTTP API，而是包含以下信息的标准组件：

- 元信息：名称、版本、描述、标签、作者、权限要求。
- 输入模型：通过 Pydantic 描述输入结构。
- 输出模型：通过 Pydantic 描述输出结构。
- 执行逻辑：用 Python 实现具体业务处理。
- 运行约束：超时、重试、资源要求、是否支持异步。
- 治理信息：日志、指标、状态、血缘、审计。

可以把算子理解为“可治理的业务函数”或“可编排的数据处理节点”。

### 3.2 算子和函数/API 的区别

| 对象 | 特点 | 问题 |
|---|---|---|
| 函数 | 调用简单，适合本地代码复用 | 缺少注册、权限、日志、血缘、版本和运行状态 |
| API | 可跨系统调用 | 接口容易碎片化，难以表达上下游关系 |
| 算子 | 有标准输入输出、元信息、版本、执行器、DAG 编排 | 设计成本更高，但适合平台化和自动化 |

## 4. 总体架构

```text
人机交互界面 / 智能体 API / 调度系统
              |
              v
        工作流编排层 DAG
              |
              v
        统一执行器 Executor
              |
              v
        算子注册中心 Registry
              |
              v
        算子服务层 Operators
              |
              v
数据库 / 文件存储 / 向量库 / 数据目录 / 业务系统
```

各层职责如下：

| 层级 | 职责 |
|---|---|
| 人机交互界面 | 给业务人员使用，负责配置任务、查看结果、审核 AI 产物 |
| 智能体 API | 给 AI、Agent、MCP、Skill 或自动化系统调用 |
| DAG 编排层 | 描述算子之间的依赖关系和数据流 |
| Executor | 统一执行算子，处理校验、权限、日志、异常、状态、指标 |
| Registry | 管理算子的注册、发现、查询、版本 |
| Operator | 执行具体业务逻辑 |
| 存储层 | 保存原始数据、中间结果、数据集、血缘、审计记录 |

## 5. 算子类型设计

### 5.1 数据接入算子

负责从外部系统读取数据，形成平台内部统一的数据引用。

典型输入：

- 数据源类型：MySQL、PostgreSQL、API、CSV、Excel、对象存储、消息队列。
- 连接信息：数据源 ID、表名、查询条件、分页规则。
- 增量规则：时间字段、主键字段、水位线。

典型输出：

- 数据集引用。
- 字段结构。
- 采集行数。
- 原始数据快照位置。

### 5.2 清洗算子

负责把原始数据处理成可用数据。

典型能力：

- 去重。
- 去噪。
- 缺失值处理。
- 字段标准化。
- 格式转换。
- 敏感字段脱敏。
- 多源数据对齐。

典型输出：

- 清洗后的数据集引用。
- 清洗规则版本。
- 被删除、修改、脱敏的数据统计。

### 5.3 标注算子

负责生成训练、检索、分析或业务解释所需的标签。

典型能力：

- 规则标注。
- 人工标注。
- LLM 辅助标注。
- 多模态标注。
- 结构关系标注。
- 标签冲突检测。

典型输出：

- 标注集引用。
- 标签体系版本。
- 标注覆盖率。
- 人工审核状态。

### 5.4 质量评估算子

负责对数据集或标注集做质量检查，形成质量门禁。

典型指标：

- 完整性。
- 准确性。
- 一致性。
- 重复率。
- 空值率。
- 标签置信度。
- 样本分布。
- 业务规则命中率。

典型输出：

- 质量评分。
- 是否通过门禁。
- 问题明细。
- 修复建议。

### 5.5 血缘算子

负责记录数据资产从产生到发布的全链路关系。

典型记录：

- 输入数据集。
- 输出数据集。
- 执行算子。
- 算子版本。
- 参数快照。
- 执行人或调用方。
- 执行时间。
- 上下游任务。

血缘算子不一定只作为独立节点存在，也可以作为 Executor 的内置能力，在每次算子执行后自动记录。

### 5.6 发布算子

负责把处理后的数据资产交付给下游。

典型发布目标：

- 数据目录。
- 数据仓库。
- 向量库。
- 知识库。
- 训练数据集。
- 业务 API。
- 文件包。
- 模型调用说明或 Skill 文档。

典型输出：

- 发布目标。
- 发布版本。
- 数据资产 ID。
- 使用说明。
- 回滚信息。

## 6. Python 模块设计

建议目录结构如下：

```text

  operators/

```

### 6.1 Schema 层

所有通用数据结构集中定义在 `schemas.py`：

```python
from typing import Any, Literal
from pydantic import BaseModel, Field


class DatasetRef(BaseModel):
    dataset_id: str
    uri: str
    format: str
    schema_: dict[str, Any] = Field(default_factory=dict, alias="schema")
    version: str | None = None


class OperatorContext(BaseModel):
    run_id: str
    tenant_id: str
    user_id: str
    source: Literal["ui", "api", "agent", "scheduler"]
    trace_id: str | None = None


class OperatorExecutionResult(BaseModel):
    status: Literal["success", "failed", "skipped"]
    output: dict[str, Any] = Field(default_factory=dict)
    metrics: dict[str, Any] = Field(default_factory=dict)
    lineage: dict[str, Any] = Field(default_factory=dict)
```

设计要点：

- `DatasetRef` 只保存数据引用，不直接在算子之间传递大数据。
- `OperatorContext` 保存运行上下文，区分 UI、API、Agent、调度系统等入口。
- 各类业务算子必须定义自己的输入输出模型。

### 6.2 Operator 抽象基类

`base.py` 定义算子的统一接口：

```python
from abc import ABC, abstractmethod
from typing import ClassVar, Generic, TypeVar
from pydantic import BaseModel

from .schemas import OperatorContext

InputT = TypeVar("InputT", bound=BaseModel)
OutputT = TypeVar("OutputT", bound=BaseModel)


class Operator(ABC, Generic[InputT, OutputT]):
    name: ClassVar[str]
    version: ClassVar[str]
    description: ClassVar[str]
    input_model: ClassVar[type[InputT]]
    output_model: ClassVar[type[OutputT]]
    required_permissions: ClassVar[list[str]] = []

    @abstractmethod
    def run(self, data: InputT, ctx: OperatorContext) -> OutputT:
        pass
```

设计要点：

- 算子必须声明名称和版本。
- 算子必须声明输入输出模型。
- 算子只实现业务逻辑，不负责权限、日志、重试、状态管理。

### 6.3 Registry 注册中心

`registry.py` 负责算子的注册和发现：

```python
from dataclasses import dataclass

from .base import Operator


@dataclass(frozen=True)
class OperatorSpec:
    name: str
    version: str
    description: str
    input_schema: dict
    output_schema: dict
    op_cls: type[Operator]


class OperatorRegistry:
    def __init__(self):
        self._items: dict[tuple[str, str], OperatorSpec] = {}

    def register(self, op_cls: type[Operator]) -> None:
        spec = OperatorSpec(
            name=op_cls.name,
            version=op_cls.version,
            description=op_cls.description,
            input_schema=op_cls.input_model.model_json_schema(),
            output_schema=op_cls.output_model.model_json_schema(),
            op_cls=op_cls,
        )
        self._items[(spec.name, spec.version)] = spec

    def get(self, name: str, version: str) -> OperatorSpec:
        return self._items[(name, version)]

    def list(self) -> list[OperatorSpec]:
        return list(self._items.values())
```

设计要点：

- Registry 对外暴露算子清单，方便 UI 展示和 Agent 查询。
- 输入输出 Schema 可以直接用于生成表单、API 文档或工具描述。
- 版本管理必须以 `(name, version)` 为唯一键。

### 6.4 Executor 执行器

`executor.py` 是所有算子的统一执行入口：

```python
from .registry import OperatorRegistry
from .schemas import OperatorContext


class OperatorExecutor:
    def __init__(self, registry: OperatorRegistry):
        self.registry = registry

    def execute(
        self,
        name: str,
        version: str,
        payload: dict,
        ctx: OperatorContext,
    ):
        spec = self.registry.get(name, version)
        op_cls = spec.op_cls

        input_data = op_cls.input_model.model_validate(payload)

        self._check_permission(op_cls.required_permissions, ctx)
        self._record_started(name, version, ctx)

        try:
            output = op_cls().run(input_data, ctx)
            output = op_cls.output_model.model_validate(output)
            self._record_success(name, version, ctx, output)
            return output
        except Exception as exc:
            self._record_failed(name, version, ctx, exc)
            raise

    def _check_permission(self, permissions: list[str], ctx: OperatorContext) -> None:
        pass

    def _record_started(self, name: str, version: str, ctx: OperatorContext) -> None:
        pass

    def _record_success(self, name: str, version: str, ctx: OperatorContext, output) -> None:
        pass

    def _record_failed(self, name: str, version: str, ctx: OperatorContext, exc: Exception) -> None:
        pass
```

设计要点：

- Executor 统一做输入校验、权限检查、日志、异常和状态记录。
- 算子内部不重复实现平台治理逻辑。
- 后续可以在 Executor 层增加重试、超时、队列、异步执行和分布式调度。

### 6.5 Workflow / DAG 层

`workflow.py` 描述算子之间的依赖关系：

```python
from pydantic import BaseModel, Field


class WorkflowNode(BaseModel):
    id: str
    operator: str
    version: str
    input: dict = Field(default_factory=dict)


class WorkflowEdge(BaseModel):
    from_node: str
    to_node: str
    output_key: str
    input_key: str


class WorkflowDefinition(BaseModel):
    name: str
    version: str
    nodes: list[WorkflowNode]
    edges: list[WorkflowEdge]
```

DAG 层只描述依赖关系，不写业务逻辑。一个典型数据资产生产流程如下：

```text
数据接入算子
  -> 清洗算子
  -> 标注算子
  -> 质量评估算子
  -> 血缘算子
  -> 发布算子
```

## 7. 示例：清洗算子

```python
from pydantic import BaseModel, Field

from data_asset_ops.base import Operator
from data_asset_ops.schemas import DatasetRef, OperatorContext


class CleanInput(BaseModel):
    dataset: DatasetRef
    rules: list[str] = Field(default_factory=list)


class CleanOutput(BaseModel):
    cleaned_dataset: DatasetRef
    removed_rows: int
    changed_rows: int
    metrics: dict


class CleanOperator(Operator[CleanInput, CleanOutput]):
    name = "clean"
    version = "1.0.0"
    description = "对数据集执行去重、脱敏、字段标准化等清洗操作"
    input_model = CleanInput
    output_model = CleanOutput
    required_permissions = ["dataset:read", "dataset:write"]

    def run(self, data: CleanInput, ctx: OperatorContext) -> CleanOutput:
        cleaned_ref = DatasetRef(
            dataset_id=f"{data.dataset.dataset_id}_cleaned",
            uri=f"{data.dataset.uri}/cleaned",
            format=data.dataset.format,
            schema=data.dataset.schema_,
            version="1.0.0",
        )

        return CleanOutput(
            cleaned_dataset=cleaned_ref,
            removed_rows=120,
            changed_rows=530,
            metrics={
                "duplicate_rate": 0.03,
                "null_rate": 0.01,
            },
        )
```

## 8. 双入口设计

原文强调系统需要同时支持人机交互界面和机器自动化调用。算子化之后，这两个入口不应该各自实现一套逻辑，而应该共享同一个 Registry 和 Executor。

```text
业务人员 UI
  -> 提交算子参数
  -> Executor 执行
  -> 返回可视化结果

Agent / API / MCP / Skill
  -> 查询 Registry 获取可用算子
  -> 按 Schema 生成参数
  -> Executor 执行
  -> 返回结构化结果
```

UI 入口适合：

- 配置数据源。
- 查看算子列表。
- 拖拽编排 DAG。
- 审核标注结果。
- 查看质量报告。
- 人工确认发布。

机器入口适合：

- 自动发现算子。
- 自动生成执行参数。
- 自动串联任务。
- 自动检查执行结果。
- 自动重试或修复。

关键点是：两种入口最终都进入同一个执行层，保证权限、日志、血缘、状态和结果一致。

## 9. 元信息设计

每个算子建议配套一个元信息文件，可以使用 `operator.yaml` 或 `SKILL.md`。

示例：

```yaml
name: clean
version: 1.0.0
description: 对数据集执行去重、脱敏、字段标准化等清洗操作
category: data_governance
input_model: CleanInput
output_model: CleanOutput
permissions:
  - dataset:read
  - dataset:write
tags:
  - 清洗
  - 脱敏
  - 去重
runtime:
  timeout_seconds: 1800
  retry: 1
  async_supported: true
```

如果要给 Agent 使用，还需要提供自然语言描述：

```text
当你需要把原始数据处理成可用于训练、检索或分析的数据集时，使用 clean 算子。
输入必须包含 dataset 和 rules。
输出会返回 cleaned_dataset、removed_rows、changed_rows 和 metrics。
```

## 10. API 设计

算子平台对外至少需要提供以下 API：

| API | 作用 |
|---|---|
| `GET /operators` | 查询算子列表 |
| `GET /operators/{name}/{version}` | 查询算子详情和输入输出 Schema |
| `POST /operators/{name}/{version}/execute` | 执行单个算子 |
| `POST /workflows` | 创建工作流 |
| `POST /workflows/{id}/runs` | 执行工作流 |
| `GET /runs/{run_id}` | 查询执行状态 |
| `GET /runs/{run_id}/logs` | 查询执行日志 |
| `GET /datasets/{id}/lineage` | 查询数据血缘 |

API 返回必须结构化，避免只返回自然语言文本。这样 UI、Agent 和调度系统都可以稳定消费。

## 11. 状态与异常

算子执行状态建议统一为：

```text
PENDING     等待执行
RUNNING     执行中
SUCCESS     执行成功
FAILED      执行失败
CANCELLED   被取消
SKIPPED     被跳过
```

异常需要区分类型：

| 异常类型 | 含义 | 处理方式 |
|---|---|---|
| 参数错误 | 输入不符合 Schema | 直接失败，返回校验错误 |
| 权限错误 | 调用方无权限 | 直接失败，记录审计 |
| 数据错误 | 数据源不可用或字段不匹配 | 失败，可给出修复建议 |
| 业务错误 | 算子逻辑判断不通过 | 失败或返回质量门禁不通过 |
| 系统错误 | 网络、存储、队列等故障 | 可重试 |

## 12. 观测与审计

Executor 每次执行算子时都应记录：

- run_id。
- workflow_id。
- operator_name。
- operator_version。
- input 摘要。
- output 摘要。
- 开始时间。
- 结束时间。
- 执行耗时。
- 调用来源：UI、API、Agent、Scheduler。
- 调用人或服务账号。
- 执行状态。
- 错误信息。
- 关键指标。
- 血缘关系。

这些信息后续可以用于：

- 任务追踪。
- 数据审计。
- 问题排查。
- 质量分析。
- 成本统计。
- Agent 自我纠错。

## 13. 权限与多租户

算子平台要避免“Agent 可以调用一切”的风险。建议把权限放在 Executor 层统一处理。

权限维度包括：

- 谁可以查看算子。
- 谁可以执行算子。
- 谁可以读取某个数据集。
- 谁可以写入某个数据集。
- 谁可以发布数据资产。
- 谁可以查看血缘和审计日志。

多租户场景下，所有数据结构都必须带 `tenant_id`，Executor 在执行前校验数据集、工作流、算子和调用方是否属于同一个租户或是否具备跨租户授权。

## 14. 版本管理

算子版本必须显式管理，原因是同一个算子的逻辑变更会影响数据资产结果。

建议规则：

- `1.0.0`：初始稳定版本。
- `1.1.0`：兼容性新增能力。
- `2.0.0`：输入输出或核心逻辑发生不兼容变化。

工作流中必须固定算子版本：

```yaml
nodes:
  - id: clean_users
    operator: clean
    version: 1.0.0
```

不能只写 `latest`，否则同一条工作流在不同时间执行可能得到不同结果。

## 15. MVP 落地范围

第一阶段不建议直接做完整平台，可以先落地一个最小闭环：

1. 定义通用 Schema：`DatasetRef`、`OperatorContext`、执行状态。
2. 实现 `Operator` 抽象基类。
3. 实现内存版 `OperatorRegistry`。
4. 实现单机版 `OperatorExecutor`。
5. 实现三个基础算子：数据接入、清洗、质量评估。
6. 实现一个 YAML/JSON 工作流定义。
7. 实现一个简单 FastAPI 接口，支持查询算子和执行算子。
8. 记录基础执行日志和数据血缘。

第二阶段再扩展：

- 标注算子。
- 发布算子。
- DAG 可视化编排。
- 异步任务队列。
- 分布式执行。
- Agent/MCP/Skill 接入。
- 多租户权限。
- 完整审计后台。

## 16. 设计收益

算子化之后，平台可以获得以下收益：

- **复用能力**：同一个清洗、标注、评估逻辑可以被多个业务流程复用。
- **统一入口**：UI、API、Agent、调度系统都调用同一套执行器。
- **可编排**：不同算子可以组合成数据资产生产流水线。
- **可治理**：每次执行都有输入、输出、日志、状态、血缘和审计。
- **可扩展**：新增能力时只需要新增算子，不需要重写平台。
- **可评估**：质量评估算子可以作为发布前门禁。
- **可回滚**：算子版本和数据集版本明确后，可以追溯和回放。
- **适合 AI 调用**：结构化 Schema 和元信息可以直接暴露给 Agent 使用。

## 17. 关键取舍

### 不把算子设计成普通函数

普通函数虽然简单，但缺少平台级治理能力。算子必须具备元信息、版本、输入输出模型和统一执行入口。

### 不让算子之间直接互相调用

算子之间如果互相调用，会重新形成耦合。依赖关系应由 DAG 层描述。

### 不让每个算子自己处理日志和权限

日志、权限、异常、状态这些能力属于平台基础设施，应该放在 Executor 层统一处理。

### 不直接在算子之间传递大对象

数据资产平台通常处理大文件、大表或多模态数据。算子之间应传递 `DatasetRef`，而不是直接传递完整数据内容。

## 18. 总结

这套算子设计的本质是把企业数据资产生产过程拆成标准化执行单元：

```text
数据接入 -> 清洗 -> 标注 -> 质量评估 -> 血缘记录 -> 发布
```

每个算子都具备清晰的输入、输出、版本、权限和执行语义。平台通过 Registry 发现算子，通过 Executor 执行算子，通过 DAG 编排算子，通过血缘和审计治理算子。

这样设计后，原来面向人的数据平台可以逐步演进为同时支持人和 AI 的数据资产工作台。业务人员可以通过 UI 使用这些能力，智能体可以通过 API 或 Skill 自动调用这些能力，最终形成可复用、可编排、可治理的数据资产生产体系。
