# project2_1 生产级热更新部署说明

## 1. 目标与边界

本版本实现了意图识别服务的生产级热更新基础能力：

- 在线预测：`POST /predict`
- 异步模型热更新：`POST /admin/reload`
- 热更新任务查询：`GET /admin/reload/{job_id}`
- 原子回滚：`POST /admin/rollback`
- 运行状态：`GET /admin/status`、`GET /health`

说明：

- 按你的要求，本实现未加入鉴权。生产上请仅暴露在内网或挂在网关后。
- `uvicorn --reload` 只用于代码自动重启开发模式，不是模型热更新机制。

## 2. 架构设计

核心组件为 `ModelManager`（见 `app.py`）：

1. 单活模型指针 `active`：在线请求始终读取当前活动模型。
2. 历史模型栈 `history`：每次热更新成功后保留旧模型，用于回滚。
3. 并发互斥：同一时刻只允许一个 reload 任务运行（并发请求会返回冲突）。
4. 异步作业：reload 在后台线程执行，接口快速返回 `job_id`。
5. 原子切换：新模型完成加载（以及可选 warmup）后才切换到活动模型。

故障行为：

- reload 失败：不影响当前在线模型。
- rollback 失败：返回错误，不切换模型。
- 预测请求：若无活动模型，返回 503。

## 3. 模型目录约定

建议每个版本一个目录，例如：

```text
models/
  intent/
    v20260314_1200/
      adapter_config.json          # LoRA 模型时存在
      adapter_model.safetensors
      label_mapping.json
    v20260315_0930/
      config.json                  # 合并模型时存在
      model.safetensors
      tokenizer.json
      label_mapping.json
```

加载逻辑：

- 目录含 `adapter_config.json`：按 LoRA 适配器加载（基础模型来自 adapter 配置或 `BASE_MODEL_NAME`）。
- 否则按完整序列分类模型加载。
- `label_mapping.json` 优先；若完整模型配置含 `id2label` 也可使用。

## 4. 启动与配置

### 4.1 环境变量

- `MODEL_PATH`：启动时默认模型目录（默认 `./qwen3-intent-lora`）
- `BASE_MODEL_NAME`：LoRA 适配器缺省基础模型名（默认 `Qwen/Qwen3-8B`）
- `REQUIRE_MODEL_ON_STARTUP`：启动时模型加载失败是否直接失败（默认 `true`）
- `MAX_HISTORY_MODELS`：回滚历史保留数量（默认 `2`）
- `MAX_RELOAD_JOBS`：内存中保留的 reload 作业记录数（默认 `30`）
- `PREDICT_MAX_LENGTH`：预测最大 token 长度（默认 `128`）

### 4.2 启动命令

```bash
python3 app.py --host 0.0.0.0 --port 8000
```

开发调试（仅开发环境）：

```bash
python3 app.py --reload
```

## 5. 发布与回滚流程（建议）

### 5.1 灰度发布流程

1. 把新模型目录发布到服务器本地（不覆盖旧目录）。
2. 调用 `POST /admin/reload` 提交新版本路径。
3. 轮询 `GET /admin/reload/{job_id}` 直到 `state=succeeded`。
4. 验证健康检查与关键样本预测。
5. 扩大流量或全量切换（多实例场景做滚动/灰度）。

### 5.2 快速回滚流程

1. 发现新版本异常（延迟、错误率、预测漂移）。
2. 调用 `POST /admin/rollback`。
3. 验证 `/health`、关键样本、业务指标恢复。

## 6. API 示例

### 6.1 预测

```bash
curl -X POST http://127.0.0.1:8000/predict \
  -H "Content-Type: application/json" \
  -d '{"text":"我要退票"}'
```

### 6.2 热更新

```bash
curl -X POST http://127.0.0.1:8000/admin/reload \
  -H "Content-Type: application/json" \
  -d '{
    "model_path":"./models/intent/v20260315_0930",
    "version":"v20260315_0930",
    "warmup_texts":["我要退票","查询余额"]
  }'
```

### 6.3 查询热更新任务

```bash
curl http://127.0.0.1:8000/admin/reload/<job_id>
```

### 6.4 回滚

```bash
curl -X POST http://127.0.0.1:8000/admin/rollback
```

## 7. 监控与告警建议

至少监控以下指标：

- `predict` QPS / p95 / p99 延迟
- `predict` 5xx 比例
- reload 成功率、平均耗时、失败原因分布
- 当前活动模型版本
- 意图分布漂移（上线前后类别占比变化）

告警建议：

- 5xx 连续 5 分钟超过阈值
- reload 连续失败
- 预测延迟显著升高

## 8. 多实例部署要点

若是多副本（K8s/容器）：

1. 先确保每个副本都能访问同一版本模型目录。
2. 分批次触发 reload（10% -> 30% -> 100%）。
3. 每一批次都做指标验收再继续。
4. 回滚同样按批次执行，防止全量抖动。

## 9. 当前实现的明确限制

- 未做接口鉴权（按本次需求）。
- reload 任务状态保存在内存中，进程重启后不会保留历史任务记录。
- 默认回滚是“回到上一个活动模型”，不是任意历史版本选择。
